# Changelog

The release workflow uses the matching `## vX.Y.Z` section below as the GitHub
Release notes. Add a section here when cutting a release; if none exists, the
workflow falls back to auto-generated notes.

## Unreleased

- **Status marks mean the same on every page, and a model that is turned off reads "Off" everywhere.** Models, Deployments, Tenants, MCP, Knowledge and Batches each drew their own dots with their own meanings: a dashed ring was maintenance on Models, not running on Deployments and archived on Tenants, and a disabled model read "Off" on Models and "Paused" on Deployments. They now share one set: a filled dot is on, a half dot in progress, a ring no data yet, a dashed ring deliberately not serving (off, suspended, archived, maintenance), and the white pill needs someone. Visible changes: Deployments says "Off" for a model turned off in Models; a deployment not seen lately is a ring; suspended tenants and turned-off keys are dashed; a model turned off is a dashed dot instead of a small square; an endpoint's health and the recent checks read "Healthy", "Failing", "Not checked yet" or "Off" instead of the gateway's raw words; a running batch is a half dot. The Playground and the assistant's result cards are monochrome too: the Playground's mode tabs, route explanation, answer links and code, mesh progress and test results lose their green, amber, sky and violet. Violet stays only as the rail beside the assistant's own messages.
- **The Playground reads its model list, pool load and voices through the dashboard's shared queries.** Each Playground tab and assistant card fetched the model list on its own, and the model picker and speech voices fetched in effects with their own error handling. They now share the pages' one model-list, fair-share and voice queries (one request for every component on a page, a list read in the last 30 s reused), and a failed model-list read shows the gateway's own reason instead of "Unable to load models from the gateway." The request panel's trace and helper-call reads and the Fairshare hooks use the same JSON reader.
- **Every dashboard chart takes its colours from the theme's chart tokens and shares one tooltip.** The Overview traffic chart, a model's traffic chart, the Reports chart, Model speed and the Fairshare history each wrote their own colours and tooltip frame; the `--chart-*` tokens in the stylesheet were unused (and green, amber and blue). The series colours, grid, axis, hover band and tooltip background now come from those tokens, and the four custom tooltips share one frame and row. Charts look the same apart from slight shade shifts: the current series is one grey (it was three close ones) and the generic tooltip's title is in the same small type as the others.
- **Numbers, money and durations read the same on every dashboard page.** Seven dollar formatters, three compact-number formatters and two duration formatters each gave their own answer, sometimes in one table row: 12,345 tokens read "12k", "12K" or "12.3K", 1,500 ms read "1.50s" or "1.5 s", and $0.004 read "$0.00", "< $0.01", "$0.004" or "$0.0040". They are now one set in `lib/format.ts`: counts are "1.2K" / "3.4M" / "1.1B" (capital K, chart axes included), durations "850 ms" / "1.5 s", and money "$4.60", "$1,235" or "$12K", with "< $0.01" below a cent except for per-request costs and prices, which keep two significant digits ("$0.0012"). Numbers are always written the en-US way ("12,345") instead of in the browser's locale, so the server and browser renders agree. Visible changes: some cells change from "1.2k" to "1.2K", budgets above $10,000 read "$12K", prices show two decimals ("$0.60 · $2.50" instead of "$0.6 · $2.5"), the request log rounds durations to one decimal, and the tenant portal's costs no longer show up to six decimals.
- **Every Management API route is in the OpenAPI document with a declared tag and real schemas, a test keeps it that way, and setters, toggles and deletes answer alike.** The document was kept in step with the router by hand: 13 replica, launch-spec and launch handlers had no tag (they showed under `crate`), `GET /api/v1/stats/daily` used an undeclared `stats` tag, three managed-model routes typed the id as a string, about 50 response and field types pointed at schemas the document did not contain (written with a module path such as `usage::UsageAgg`, or never registered, like the advice and router-readiness types), the audit log documented a hand-copied twin of its row, and the request-log and breakdown rows were documented without the names the gateway adds. A test now reads the router and fails on any route that is missing from the document, has no declared tag or leaves a path parameter undocumented, on any documented operation no route serves, and on any schema reference that resolves to nothing; all of the above are fixed. Behaviour changes: `PUT /api/v1/keys/{id}/disabled`, `/tracing`, `/end-user-fairshare` and `/background` answer `200` with the updated key, and `PUT /api/v1/tenants/{id}/tracing` and `/synthetic` `200` with the updated tenant, instead of `204` with no body (`/tenants/{id}/synthetic` also answers 404 for a missing tenant, as the others did). The tenant setters (`status`, `schedule`, `budget`, `allowlist`, `guardrails`, `compression`, `weight`, `group`) and `/fairshare/groups/{name}/weight` are documented as `PUT`, like every other single-setting write; `PATCH` still works on them for one release. `DELETE /api/v1/models/{id}/managed` answers `204` instead of `200 {"deleted": true}`, and both it and `DELETE /api/v1/knowledge/collections/{id}` answer `404` when there is nothing to delete instead of reporting success. The dashboard uses `PUT` and reads the returned rows; Voyager's `PUT /keys/{id}/disabled` call reads the body only when there is one, so it is unaffected. The four key toggles share one store write and one handler path, which returns the row the update already read.
- **Every environment setting is read once at boot by obleth-config, with one parser, and a bad value is either a warning or a refusal to start, never silent.** Settings were read in a dozen places (the batch runner, the SSRF policy, the compressor, the client-address rules, the admission and stream-idle timeouts, video job retention, the crash guard, session ids, JWT issuers), each with its own parser: most took an unreadable value as the default without a word, the SSRF allow-list dropped entries it could not parse, a bad strict flag panicked and a bad `OBLETH_JWT_ISSUERS` exited with code 2 before logging was up. They are now fields of `Config`, read by one reader that trims each value and treats blank as unset. A value that cannot be read (`OBLETH_GLOBAL_MAX_IN_FLIGHT=4k`, a zero timeout, `OBLETH_BATCH_WINDOW_MIN=10m`, a trusted-proxy entry that is not a CIDR, an invalid `OBLETH_KEY_PREFIX`) is logged as a warning at boot, naming the variable, the value and the default used. Settings the gateway must not guess at stop the start, all listed in one `refusing to start:` error: a missing `OBLETH_ADMIN_TOKEN`, an unreadable `OBLETH_FAIL_OPEN` or `OBLETH_SCHEMA_VERIFY_ONLY`, a bad `OBLETH_JWT_ISSUERS`, and now also any entry of `OBLETH_ALLOWED_PRIVATE_CIDRS` that is not an IP or CIDR and an unreadable `OBLETH_BLOCK_PRIVATE_NETWORKS`. Upgrade notes: a gateway whose `OBLETH_ALLOWED_PRIVATE_CIDRS` holds a typo, which used to start with that entry ignored, now refuses to start until it is fixed; `OBLETH_BLOCK_PRIVATE_NETWORKS=enabled` (or any other unreadable value) used to mean off and now refuses to start; `OBLETH_BATCH_RUNNER` set to something unreadable (such as `enabled`) used to turn the runner off and now warns and leaves it on, so write `false` to turn it off. The chart and Compose defaults are all valid.
- **The global ceiling saved with `PUT /api/v1/capacity` applies on every replica and survives restarts, alert settings reach every replica at once, and saved settings share one store helper.** `PUT /api/v1/capacity` changed only the replica that answered and was lost at its next restart, while the audit log said it was made; a saved alert target reached the other replicas only on their 15 s re-read. The ceiling is now saved in Postgres (`app_settings`, key `capacity`), and a save of either setting tells every replica on the invalidation channel (`settings:alerts`, `settings:capacity`; older releases ignore it) to re-read it at once, with the 15 s re-read kept as a fallback, also after a backup restore. New: `DELETE /api/v1/capacity` clears the saved ceiling; `GET`, `PUT` and `DELETE /api/v1/capacity` answer `source` (`saved` or `environment`) and `environment_max_in_flight`; `/fairshare/live` adds `hard_ceiling_source`, and the Fairshare page says where the ceiling comes from. `PUT` with `max_in_flight: 0` is now a 400 (it was read as 1). The eleven saved-settings get/put pairs in the store are one-line wrappers over one reader and one writer; the legacy `charo_enabled` key is still written with the Charo settings. **Upgrade note:** after a ceiling is saved it wins over `OBLETH_GLOBAL_MAX_IN_FLIGHT` on every replica, also after a restart, so changing the variable and rolling the pods no longer changes the ceiling until `DELETE /api/v1/capacity` clears the saved one. The variable only seeds the ceiling while nothing is saved.
- **A tenant's `served_tokens` means the same in a gateway's own fairshare view and the cluster view, and rows tied on score keep their order.** In shared mode the cluster view gave a tenant its service without the clock it was placed at on joining, while a gateway's own view (and the scheduler) used the whole score, so a tenant that joined late read as far behind, and next in line, in one scope and level in the other. Gateways now publish the score the scheduler ranks by, so `served_tokens` and `share_score` read the same in `replica` and `cluster` scope (summed over gateways in the latter); a group's is unchanged. Tenant and key rows are sorted lowest score first with ties broken by id in both scopes, where a gateway's own view left tied rows (such as tenants that just joined) in a different order on each poll. The three cluster-wide reads share one shared-mode check and one named 1 s bound, and the history sampler's cluster sample starts from the gateway's own pool totals instead of building its tenant and key rows every 2 s. During a rolling upgrade a tenant's cluster `served_tokens` can mix both meanings until every gateway runs this release.
- **The Slurm sheet's API version, version list and Slurm release come from the provisioner, so every replica shows the same, and the launcher's Slurm reads run at once.** They were held in one gateway process, filled only by a connection test or a resource read on it, so with several replicas they showed on one request and not the next, and were empty after every restart until someone pressed Test. The provisioner now reports them with each tick (the version it actually used, the versions slurmrestd lists, read at most every ten minutes, and the release), the gateway keeps them with the tick status in Redis, and the sheet shows them for the saved URL and user; a tick that could not reach slurmrestd keeps the last ones. Until a provisioner with this change has ticked, the version shows the pinned one (none for `auto`) and the list and release are empty. The launcher's `GET /api/v1/slurm/resources` sends its partitions, nodes and accounts reads together, so a slow or down slurmrestd costs one timeout instead of three, and it and the connection test share one HTTP client (10 s timeout) instead of building one per call.
- **A Redis fault while looking up a model or MCP server is answered 503 with `Retry-After`, not 404.** When a replica had not cached a model (or MCP server) and Redis failed or timed out, the request got `404 model '<name>' is not registered`, which SDKs do not retry and people read as a configuration error. It now gets `503 model registry unavailable; try again shortly` (`mcp server registry unavailable; try again shortly` on `/mcp/{server}`) with `Retry-After: 5`, the same as an admission timeout; the alert and log are unchanged. A model Redis does not know is still a 404. **Upgrade note:** during a Redis fault, clients see retryable 503s for models this replica had not cached instead of 404s.
- **`GET /api/v1/fairshare/live` sends the slots each pool's requests hold (`slots`).** A background request holds one slot per `OBLETH_BACKGROUND_SLOT_TOKENS` of prompt, so a background pool could read 4 in flight against a cap of 12 while every slot was taken. Each pool entry now carries `slots` beside `in_flight`, in the view's scope (summed across replicas in cluster scope, the prober's one slot left out); an ordinary pool's slots are its requests.
- **The API keys page reads one page of keys at a time, searched, filtered and sorted by the gateway across every key.** It read every key, every capped key's budget and the 5,000 busiest keys' 30-day use on each load, then filtered and sorted in the browser (keys past the 5,000 showed no use). Now it reads 100 keys and only their use and budgets, with **Load more** for the next 100; the search (which now also matches a key's tenant name and identity issuer) and every filter (tenant, on/off, kind, budget capped, none or near, unused for 30 days) run in the gateway. `GET /api/v1/keys` gains `disabled`, `kind`, `budget`, `unused`, `sort` (`created`, `name`, `last_used`, `requests`, `tokens`, `cost`, `budget`), `dir`, `since_ms`/`until_ms` and an opaque `cursor` holding the last key's sort value and id (`x-obleth-next-cursor` while more follow). The created and name orders are Postgres keyset pages; the use orders rank keys in ClickHouse over the window, a page plus one at a time (about 0.15 s over 20M rows and 50,000 keys), with unused keys after them by name; the budget order ranks capped keys by the share of their cap used. New: `GET /api/v1/keys/count` (keys matching the filters), `GET /api/v1/keys/stats` (the page's tiles in one ClickHouse read), `?ids=` on `/budgets/usage` and `?key_id=`/`until_ms` on `/usage/keys/summary`. Select all takes the keys shown; **Select every matching key** acts on everything the search and filters match, by filter on the server, after a confirm that gives the gateway's count and how many are not on the page, and changes nothing if the count no longer holds. `GET /keys` without the new parameters answers as before.
- **Background work holds a model's slots by prompt length, so long batch prompts no longer slow every interactive stream.** A batch item or a background key's request held one slot whatever its prompt, so a batch of 13,000-token prompts filled its whole share (64 of 128 slots on a 16-pod model) and the pods kept prefilling those prompts between everyone's decode steps: no interactive request waited, but streams on the model fell from 20-30 to about 7 tokens/s. A background request now holds one slot per `OBLETH_BACKGROUND_SLOT_TOKENS` of prompt (default 4096; chart `obleth.batches.slotTokens`), from the gateway's existing prompt estimate, capped at the background share so a larger prompt still runs alone; at a 0.5 share of 128 slots that is about 16 such prompts at once instead of 64, while short-prompt batches run as before. The share, the interactive pool's room and the shared slot counts across replicas all count slots, every slot comes back together on completion, abort, error, or a replica's expiry, and the live view shows a pool's `slots` next to its `in_flight`. Interactive requests still hold one slot each, and background work still runs only while no interactive request for the model waits. `0` turns it off.
- **The Playground no longer re-parses every answer's markdown on each streamed token or keystroke.** Each token re-rendered the whole conversation, and every answer parsed its markdown again with a fresh set of plugins and components; typing in the message box did the same. Answers now render one turn at a time and only when that turn changes, the markdown renderer is memoised with its plugins and components built once, and streamed tokens land at most once per animation frame. The rest of a stream's changes, its end, a stop or an error apply any tokens still waiting first, so no text is dropped, and tokens still waiting when the page closes are saved with the conversation. The message box keeps its own text, so typing re-renders only the box.
- **The dashboard drops code nothing used.** The docked assistant (its corner window, launcher, draggable companion and sprite artwork) was no longer mounted anywhere; it is deleted, and the Playground's answer renderer keeps only what the Playground shows. Eight `/api/live` routes that no page called are gone (`budgets`, `recipes`, `recipes/{id}`, `models/validate`, `slurm/status`, `models/{id}/managed`, its `provision-error`, `settings/knowledge`); the pages reach the same gateway calls on the server. Also removed: two unused server actions (deploy a recipe by id, clear lost replicas); the Management API client's unused methods (`setModelWeight`, `usageByKey`, `keyUsage`, `usageSeries`, `costs`, `getBatch`); the API Keys page's fallback to the per-key usage endpoint that predates the summary; an unread `deviceId` log filter; `formatUsd` and `requireSession`; six unused components (`dashboard-primitives`, `model-metrics-detail`, `utilization-gauge`, `edit-form`, `ui/checkbox`, `ui/tabs`); `modelTypeHint` and the capability fields' unused stacked layout; and nine dependencies nothing imports (`framer-motion`, `bcryptjs`, `date-fns`, `jose` and five Radix packages). Seven settings actions that only other actions call are no longer exported as server actions. Nothing a user sees changes, except that the Playground's typing dots now pulse (their animation lived in the docked window's styles).
- **The OpenAPI description gives the bulk health check's real path.** It listed `POST /api/v1/models/health/check`, which no route serves (404); the bulk check is `POST /api/v1/models/health`. The dashboard's API client carried an unused method for the wrong path; it is removed.
- **Lossy compression cuts only by the compressor sidecar's scores.** Without them it dropped whole lines by a length-and-keyword heuristic, run inline on the gateway's request threads (about 10 µs per KB of new prose, 2 ms for a 200 KB segment), so with lossy on for everyone the gateway would spend that on every request, and cut by a cruder measure than the sidecar's. A new segment the sidecar did not score (none set up, busy, timed out, breaker open, or over its sentence budget) is now left whole, and with no sidecar set up the pass does not run. The gateway also stops reading a segment once it is past the sentences left in the budget, instead of splitting every candidate in the history on every request. Forms kept from earlier turns are still given. The `boon:compression` span's `scorer` is `none` when no call was made (was `heuristic`).
- **A streamed speculation answer is recorded as streamed.** Its usage row said `streamed = false` and so recorded no time to first token, which left speculation streams out of every latency figure and counted them as buffered replies.
- **Rust images compile their dependencies in a cached layer, a release re-tags the amd64 edge image of its commit, and CI gates on clippy and the lockfile.** The obleth, obleth-provisioner and benchmark-backend images compiled every dependency on each build; a cargo-chef stage now cooks them in a layer that changes only with the manifests and `Cargo.lock`, so a source-only change rebuilds just the workspace crates. Every build uses `--locked`, so a stale lockfile fails it. The build timestamp in `/api/v1/version` is now the commit time (was the build's clock), the same for every build of one commit. A release no longer builds amd64 when docker-edge already built the tagged commit: it re-tags the `:dev` or `:main` image whose `org.opencontainers.image.revision` label is the tag's commit (waiting for an edge build of it still running) and builds only when none matches; arm64 still builds, and a re-tagged image carries no `org.opencontainers.image.version` label. CI runs Rust 1.95 from the new `rust-toolchain.toml` (the builder images' release), runs clippy with `-D warnings`, passes `--locked` to every cargo call, checks benchmark-backend and obench instead of building them for release, and installs the compressor test deps with the bounds `requirements.txt` gives them. The existing clippy warnings are fixed; two displaced `#[allow]`s (`result_large_err`, `too_many_arguments`) are back on the functions they were written for.
- **A committed speculation stream no longer pauses at every check.** The stream released a verified span, then read more draft, then waited for the next check, so each check (about 300 ms) showed as a stall. Drafting and checking now run in their own task and hand verified spans to the stream, which only plays them back, so the next span is checked while the current one plays. A client that disconnects stops the task, and the request still settles once. Shipped and escalated answers are the same as before.
- **Models with the tool loop or speculation no longer copy the whole request two or three times per request.** The tool loop kept its own copy of the enriched request at enrichment, and the buffered loop copied it again before reading the first reply, for follow-up turns most requests never make; it now takes the request as it was dispatched and copies it only when a gateway tool call needs a follow-up turn. Each follow-up call no longer copies the request to send it, and speculation keeps the request without its messages, which it already holds once.
- **One reader for the streamed turns of the tool loop and speculation.** The tool loop's turns, its final turn, the speculation drafter and the continuation relay each read the upstream stream with their own copy of the same loop; they now share one `TurnReader`, and the tool loop shares one turn record and one closing sequence. The tool loop no longer copies each chunk twice, copies the turn's id and model only when they change, and records time to first token once. Clients see the same bytes.
- **The gateway's tool calls from one model reply run at the same time.** Both tool loops ran them one after another, so a reply with three 2-second searches took 6 s; they now run together, up to 8 at once and 4 at once against one MCP server, and their results go back in call order. The web-search and image limits are shared out among the calls in call order before any runs, so a call past a limit is refused as before; a reserved search whose query policy then blocks it does not give its slot to a later call of the same reply. The MCP sessions a reply needs are opened together before its calls. In a stream, the reply's "searching" markers now all go out before the calls run. MCP servers may see concurrent calls from one request.
- **Speculation scores drafts without building the verifier's reply into a tree, tokenizes the prompt while the drafter starts, and bills the target's cached prompt tokens.** Each scoring parsed the whole `prompt_logprobs` reply (megabytes for a long prompt) into JSON, then copied it; it now reads only the sent token's rank and log-probability at each draft position and skips the rest unread, with the same decisions. The prompt is no longer copied per scoring. The scoring prefix is tokenized alongside the draft call instead of after the first draft chunk, and the think-block closer is tokenized once per model, not once per request. After an escalation the request settles with the target's own usage, cached prompt tokens included (they were recorded as 0; cost was unaffected), and the usage chunk a client asked for carries them. **Removed:** `speculation_verify_model`, which was stored and returned but never read; a stored value still loads, and a client that sends it is ignored.
- **`GET /api/v1/keys` searches and sends only the fields asked for; pages that only name keys ask for just that.** New: `?q=` keeps keys whose name, prefix, description or identity subject contains the text, ignoring case (its `%` and `_` taken literally), and pages with `limit` and `after` like the full list; `?fields=id,name,key_prefix,tenant_id` sends only those fields of each key (an unknown field is a `400`). The Request logs, Reports and Audit pages and the usage export read only key ids, names, prefixes and tenants, and the Tenants page only each key's tenant and on/off state, instead of every key's full settings. Replacing a key and bulk key actions already read keys by id. The audit log's search shares the key search's pattern escaping (unchanged behaviour).
- **Knowledge uploads and backup export and restore pass through the dashboard instead of being held and rewritten in it.** A document upload (up to about 67 MB of base64 JSON) was parsed into an object in the 512Mi dashboard pod and serialised again before going to the gateway, and an export was parsed and re-indented, so two large uploads at once could run the pod out of memory. An upload now streams on to the gateway as it arrives, with its Content-Type, and the gateway's answer comes back as it is; the gateway already checks the size against the knowledge settings and that the file is text, and the dashboard still refuses a declared length over the gateway's limit before sending anything. Closing the page stops the upload at the gateway. The export streams the gateway's file through (it is no longer re-indented, so it downloads as the gateway writes it) and now records who exported it in the audit log. A restore checks the file's format once and sends the file's own text instead of a re-serialised copy. The chart's memory limit and Next.js body limits are unchanged.
- **A live poll on Models, a model's page or a deployment's page re-renders only the numbers that changed.** Every fair-share poll rebuilt each Models row and the whole model page, its settings forms included, because the load was read at the top and the rows and sections got new callbacks each time. The load is now read by small cells (the Load now column, the Load now tile, the Capacity card's line and count, a deployment's Pool now tile and chart) that watch only their model's numbers; rows and settings sections are memoised with stable callbacks. A model's page also watches only its own capacity discovery status. A deployment's launch settings form is memoised too, and the deployment reads no longer carry a read time, so a poll that changed nothing changes nothing on the page. Unsaved edits were already kept across polls and still are.
- **A deployment's page reads only its own deployment, and the Deployments list reads 24 h usage and recipes only where they are shown.** A deployment's page polled the whole fleet every 10 or 15 s (every model, launch setting and replica, plus a 24-hour ClickHouse aggregation it never showed) to build rows for every deployment and keep one. It now polls `/api/live/deployments/{id}`, which reads that model's launch settings and replicas through the per-model endpoints (and capacity discovery only for a model a Kubernetes cluster runs). The list still polls the fleet every 15 s, but its 24 h request counts are their own read once a minute, so neither the list's first load nor its poll waits on ClickHouse (the column shows a dash until they arrive). The list loads the recipes (every recipe's text and scripts) only when the Recipes tab is opened, and switching tabs no longer reloads the page on the server. Recipe cards no longer carry `scriptBody`, a rendered copy of each script nothing read.
- **One SSE reader for every stream the gateway reads.** The failure watch, the output monitor, the usage filter, the energy stamp, the Responses and Messages translators, the tool-stream loops and speculation each split upstream streams with their own parser, and the copies disagreed on line endings, multi-line data and caps. They now share one incremental splitter (`sse.rs`) that reuses its buffer, scans each byte once and hands a long event out in parts instead of holding it. The usage filter and the energy stamp are one pass (`UsageRewriter`), so a chunk is searched for usage once, and the response cache still stores the answer without the energy added. Differences: an event's data is its `data:` lines joined as the SSE specification reads them (every upstream in use sends one line per event); a blank line written `\n\r\n` now ends an event; the translators also read a last event the upstream closed without a blank line; an `event: error` over 64 KB is treated as generated content, like any other event that long. `now_ms` and the byte search are one function each in the proxy.
- **Gateway boot no longer sends about 35 ClickHouse ALTERs, and the telemetry flushers share one loop.** The `usage` columns are listed once; the CREATE TABLE and one ALTER that brings an older table up to date are generated from the list, and the ALTER (with the spans table's) runs once per schema version, recorded in `usage_meta` (`usage_schema_v1`, `spans_schema_v1`); a test fails if the list changes without a new version. The usage and spans flushers run one batch loop and every insert goes through one helper with a named 5 s timeout. `TelemetrySink::start` loses its ignored `fail_open` argument. The batch size stays at 500 rows.
- **A request naming a model family, or a name the Messages surface serves with its default model, no longer costs a Redis lookup every time.** Model names Redis did not know were never remembered; a miss is now remembered for 30 s per pod, and forgotten on every pod as soon as a model by that name is published (create, rename, re-sync or re-warm).
- **The crash guard no longer costs a Redis lookup on every routed request.** It read each request's strike count, hashed the body through a full copy of each field and allocated a model name per request. A strike now marks its model in a small sorted set (`obleth:crashrecent`) and tells the other replicas at once (a `crash:{model}` message on the invalidation channel; older releases ignore it); every replica reads the set once a minute too. Only requests to a model marked within its strike TTL are looked up, and every request is looked up while a replica does not know (at start, until its first read, or after a failed one). Fingerprints are hashed without the copy and are unchanged, so recorded strikes still match.
- **One re-warm routine for the gateway's timer and the admin resync.** `POST /api/v1/resync` (and a backup restore) pushed models and MCP servers one awaited call each, with a database read per model, and walked Redis three times; it now runs the gateway's re-warm pass (each namespace pushed pipelined, one SCAN for all three, entries created or deleted mid-pass settled) and then publishes one invalidation of everything. It still reads Postgres again after its prune every time, so an entry deleted mid-resync is evicted at once; the timer re-reads only when the prune removed something. `mcp_servers_pruned` in its report now counts servers evicted (it counted servers pruned, including ones restored). Each replica starts its re-warm timer up to a tenth of `OBLETH_REDIS_REWARM_SECS` later, so replicas started together no longer push at the same moment.
- **Batch output files stream in pages of at most 8 MB, with each answer as stored.** A page was 500 lines whatever their size, so an embeddings batch could hold hundreds of megabytes of answers, and each answer was parsed into a JSON tree and written out again. A page now also stops at 8 MB of stored answers (at least one line), and each answer is checked as JSON without being built and goes into its line as the backend sent it; one with line breaks, or not JSON, is handled as before. Answers are no longer re-written, so a body keeps the backend's key order and number formatting (it was re-sorted by key). The batch runner reuses its list of runnable batches on the wakes an item finishing causes and reads it again only on its 1 s tick.
- **Lossy compaction no longer changes earlier turns every turn.** Which sentences a segment kept depended on the latest question and on which segments were the largest that turn, so the prompt prefix changed on every request and the backend's prompt cache missed it. A segment is now compacted once, on the turn it first appears, and its form is kept in Redis next to its original (same TTL, per tenant, keyed by a version and the keep ratio) and given again on later turns. Only new segments are compacted, biased toward the question, scored by the sidecar and counted toward `max_lossy_segments`. The `boon:compression` span records `lossy_reused`.
- **The dedup, log and lossy passes share one segment index and one shape.** Each pass walked the body again, copied every eligible segment and classified it again, and each stashed its originals in its own Redis call. The segments are now found once (classified at most once, on first use), the passes record their rewrites and only replaced segments are copied, and the originals go out in one round trip. A segment one pass replaced is no longer offered to the next. All four passes report the same stats (`examined`, `replaced`, tokens before and after), which the `boon:compression` span now carries under `passes`, and each text pass stops after `max_lossy_segments` replacements (lossy counted attempts). Lossy now matches the question's words as whole words, in linear time: a 200 KB question was a lines-times-terms substring scan, and a term no longer matches inside a longer word (`config` in `configuration`). The log template miner compares a line only with templates of its length, borrows its tokens and keeps at most 512 templates; its output is unchanged. The dedup and log output are byte-identical, pinned by a digest test; lossy has its own digest.
- **Lossless compression parses each segment once and stops at 8 MB read.** A JSON segment was parsed four or five times and each table built two or three times per turn; the parsed value is now handed down (one parse per segment or embedded span, plus the round-trip check of the compacted text), qualifying an array no longer encodes it, and cells are written straight into the table. The safety guard counted only segments that shrank, so segments that could not shrink were read without limit; the pass now reads at most 8 MB of segment text per request. The compacted output is byte-identical, pinned by a digest test over the corpus and 400 fuzzed payloads.
- **Knowledge retrieval scores faster and off the request thread; vision keys hash without a copy.** Each chunk's score is a dot product summed in eight lanes (SIMD-friendly), and only the best `top_k` are sorted after a linear-time selection, ties still by position. A collection of more than 4,096 chunks is scanned on the blocking pool, so it does not stall other requests on the same worker. The query vector is shared between collections instead of copied, and keeping it in Redis no longer delays the turn. The vision boon hashes each image in place (the keys are unchanged, so kept descriptions are still found) and, past 4 MB of inline images, off the async worker.
- **Keys, Tenants, People, Audit and Request logs stay responsive on long lists.** Each re-rendered every row on every keystroke, checkbox or poll. Rows are now memoised, searches catch up when typing pauses, and Keys, Tenants and People show the first 100 rows with Show more (Select all on Keys still takes every matching key, and says how many). A key's network summary is worked out once per load. The Tenants page gets each tenant's key counts instead of every key. Audit finds each change's previous one in one pass instead of searching the list per line. On Request logs, the 5-second clock re-renders only rows from the last hour, and the filter menus are built once.
- **A knowledge collection's page renders once and reads only its own documents.** Opening it refreshed the server data at once, so it rendered twice, and each render read the documents of every collection. It now refreshes only when its last document finishes indexing, and reads one collection's documents.
- **Guardrails scan text in one pass and copy it only to redact.** The prompt-injection check ran 25 regex passes over the text; it is now one `RegexSet` pass with the same patterns and Unicode word boundaries. Detecting PII or a banned keyword no longer copies the text, redaction copies only text it changes, and reading a completion's output for scanning no longer clones the whole completion. Verdicts and redactions are unchanged.
- **Reports stays responsive with many teams and keys.** It rebuilt its chart and whole breakdown table on every keystroke in the row filter and sent every tenant's and key's full settings to the browser. The chart and table are now computed only when their data or settings change, the filter catches up when typing pauses, the table shows its first 300 rows with a Show all button, and Reports (like Request logs, through the same helper) sends only team names and key names, prefixes and teams.
- **Image, search and verdict runs in the Playground can be stopped, and closing the page stops them at the gateway.** The image, search, verdicts and 3D relays ignored the browser leaving, so a closed tab left the gateway generating (and billing); they now pass the request's abort on, as speech already did. The image, search and verdict workspaces gain a Stop button, and leaving the workspace or switching sessions stops a run in flight. The Playground saved every session to browser storage on each keystroke; it now saves once typing pauses (500 ms) and at once when the page is hidden.
- **Refused key uses now expire after 35 days, trace spans and refusals drop whole parts, and two more ledger reads prune by day.** `key_rejections` was never pruned; it now has a table TTL of 35 days (above the longest 31-day reader), applied once at startup to existing tables, so rows older than that are deleted on upgrade. It and `spans` set `ttl_only_drop_parts`, so expiry drops parts instead of rewriting them. A changed client address retention is one `ALTER` per table (was one per column). The model-health traffic check and Advice's output-length read now bound the partition column `ts` like every other ledger read, so they skip whole days outside their window.
- **The dashboard gives up on a stalled gateway and reads the session once per page.** Its Management API calls had no time limit, so a gateway that stopped answering held pages for up to 5 minutes; reads now give up after 35 s (just over the gateway's own 30 s limit on a usage read), writes after 2 minutes, and health checks of every model, autotune, resync, backup export and restore, model export and import, document upload and collection reindex after 10 minutes. A read that gives up shows the page's fallback. The GitHub release check gives up after 3 s, so an air-gapped install no longer waits on it. The signed-in session, read by both the layout and the page, is now one Postgres read per request instead of two.
- **The Slurm provisioner's tick looks jobs up and probes replicas concurrently, keeps a fixed rate, reads endpoints once, and logs on change.** It looked up each tracked job and probed each replica one after another, so a tick grew with the fleet and stretched the self-heal window counted in ticks; lookups now run 8 at a time (`OBLETH_PROVISIONER_LOOKUP_CONCURRENCY`, any error still holds the tick), every replica's ports are probed at once (up to 64 replicas), and ticks start at a fixed rate, warning once when one overruns the interval. It read endpoints once per managed model; one `GET /api/v1/endpoints` (new: every model's endpoints, each with its `model_id`) now serves the tick. It logged an info line per replica every tick; a probe result is now logged at info when it changes and a drain when it starts, with repeats at debug, and Compose and Helm default `RUST_LOG` to `info` (was `info,obleth_provisioner=debug`). A tick that keeps failing with the same error (an expired Slurm token, say) warns once instead of every 15 s.
- **The compression sidecar's README describes how it runs now, with the int8 model measured.** It documents chunked scoring, the queue and timeout, every environment variable and build arg, and the load-test options `--mixed` and `--deadline-ms`; the sweep script's thread example now uses `COMPRESSOR_NUM_THREADS`, which the sidecar reads (it named `OMP_NUM_THREADS`). The int8 model (`ONNX_FILE=onnx/kompress-int8-wo.onnx`) ranks sentences almost as fp32 does (0.977 overlap of the half kept, Spearman 0.995) at half the memory, but scored 30% slower on 4 cores, so fp32 stays the default; the Dockerfile no longer calls int8 faster.
- **The compression sidecar scores a request's sentences by length, stops when the gateway stops waiting, and sheds load.** It scored each segment separately in arrival order, so short sentences were padded to the longest one in their batch and a many-segment request made many small model calls; it now sorts all of a request's sentences by length and scores them in chunks of 8 (`COMPRESSOR_MAX_BATCH`), which on mixed chat prose is about a third faster (17 to 25-33 sentences a second on a 4-core pod, same scores within 0.001 and the same ranking). The gateway now sends its timeout (`x-obleth-timeout-ms`); the sidecar runs one request at a time (`compressor.concurrency`), lets 8 wait (`compressor.maxWaiting`), answers 503 past that and 504 once the timeout has passed, instead of scoring for up to a minute after the gateway gave up. The gateway records those as `busy` (not an error, no warning, no step toward the breaker) and leaves new prose whole. It also sends only as many sentences as a pod can score within its timeout (24 at the default 800 ms, was up to 2,048).
- **Auto routing and variants hand out shared models instead of copies.** Router candidates held their model by value, so every `auto` request copied the chosen model (about 55 fields, endpoints and boons included) once or more, and a sticky escalation copied the whole pool it narrowed to. Candidates now share the model built at each registry refresh, and the router returns that shared copy. A request for a model variant built the variant's route (the parent's with the variant's boons) on every request; it is now built once and kept under the variant's name, dropped whenever the model is invalidated (the admin invalidates every name a model answers to) and after 5 minutes, as the model cache is.
- **The scheduler skips idle pools sooner and answers narrow questions narrowly.** Each dispatch pass worked out every known pool's fill limit (and copied its name) before checking whether it had anything queued; it now checks first, so a gateway with many quiet models does less per pass. With session affinity in shared mode, looking for a request to try a held slot scanned every pool's queue twice whether or not one existed; it now scans for the request first. The batch runner read the full fair-share snapshot (every pool's tenants and keys) on every tick to learn how many items wait per key; it now asks for just that. In shared mode, the live view and model load read this replica's pool counts without building tenant and key rows the cluster view replaces. No scheduling decision changes.
- **One key by id, keys by ids, paged keys, one tenant's budgets, and one way to say a list was cut.** The dashboard read the whole key fleet to find one key (replacing a key) or a handful (bulk actions), and every budget in the fleet to show one tenant's. New: `GET /api/v1/keys/{id}`; `GET /keys?ids=a,b` (up to 200); `GET /keys?limit=&after=` pages in creation order; `GET /budgets/usage?tenant_id=`, which also reads only keys that have a cap. `GET /keys` without `limit` still returns every key as one array. Paged lists now all say when more rows follow with `x-obleth-truncated: true`: `/keys`, `/audit` and `/usage/logs` join `/usage/key-sources` and `/usage/key-rejections` (`/batches` keeps `has_more`, as OpenAI's list does). `/keys` now orders keys created in the same instant by id.
- **The request log, its facets and key-sources read far less of the ledger.** The live request log (polled every 5 s) read all 36 columns of every row in the window to return 50; it now finds the page's rows from their time and id alone, then reads every column of just those rows. The log facets ran seven scans per call, one per dimension plus the failures list; they now come from one. `key-sources` worked out each key's first-seen network by scanning up to 91 days of raw ledger on every call; a new ClickHouse table, `key_network_seen` (fed by a materialized view like `key_country_seen`, kept as long as client addresses are, and seeded once from the ledger at the first start), now holds it. `key-sources` also gets the 10-second limit and `x-obleth-truncated` header `key-rejections` has. Responses are unchanged. Two ClickHouse tests that had started failing as their fixed timestamps aged past the 90-day address TTL now write recent rows.
- **The dashboard Overview loads in one read from two ledger scans, and the footer totals are shared for 15 seconds.** Each Overview refresh made seven admin calls: the window's totals, the previous window's totals, a series, per-model usage, per-tenant usage, cache counts and the full tenant list for names; six of them scanned the same ClickHouse window. The new `GET /api/v1/overview` returns all of it, with tenant names, from two scans run together, and the control plane uses it. The footer polls `/overview/summary` every 30 s from every open page; each replica now runs that read (and the Overview's) at most once per 15 s, and callers that arrive while it runs wait for it, so totals can be up to 15 s stale. The Top tenants panel always shows spend.
- **A changed knowledge document reloads only its own chunks.** When a collection changed, every gateway replica reloaded every chunk of the collection (text and embedding) to serve the next search, so re-indexing one file in a large collection copied the whole collection out of Postgres on each replica. A refresh now reads the collection's document list, loads chunks only for documents that are new or have a new generation, keeps the rest from the previous load, and drops deleted documents. A full reload still runs every 30 minutes as a safety net. Search results are unchanged.
- **Knowledge collection sizes are read from document rows, and the search preview reads text only for its hits.** Every collection read (one collection's page, or a name lookup behind it) summed every chunk of every collection, and the chunk cap check on each indexed document counted the collection's chunk table; Postgres migration `0049` stores each document's size with its chunk count when it is indexed (filled in for documents already indexed), and both now add up document rows, for one collection when one is asked for. The search preview loaded every chunk's text and copied every embedding to score a query; it now scores the embeddings in place and fetches the text of the hits.
- **A finished request settles in one Redis round trip, and budgets keep time by the Redis clock.** After an answer, the gateway made up to four Redis calls one after another (store the cached response, refund or charge the per-minute bucket, commit the tenant's and the key's term usage) before the request was recorded; they now go out together. The per-minute token buckets and the crash guard's strike window took the time from whichever gateway pod ran the script, so clock skew between pods gave a bucket tokens it had not earned or took some away; they now use the Redis server's clock, as the shared fair-share slots already did. The unused check-only reserve and its script are gone.
- **Keys, models and MCP servers go to Redis in pipelined batches, and the re-warm scans Redis once.** Every replica re-pushed every key one `SET` at a time every 5 minutes (and at start), then scanned the whole Redis keyspace three times to prune keys, models and MCP servers; it now writes 200 entries per round trip and prunes all three namespaces from one scan. A tenant edit re-pushed the tenant's keys one at a time and a fair-share group's weight change read every key in the fleet to find the group's; both now use the pipelined push, and the group read asks Postgres for that group's keys only. Deleting a tenant evicts its keys and publishes their invalidations pipelined too. Invalidation messages are typed in code; their wire format is unchanged, so replicas of both versions share the channel during a rollout.
- **The gateway applies only the schema files a database has not recorded.** Every start re-ran all 47 Postgres schema files, taking `ACCESS EXCLUSIVE` locks on live tables about a hundred times while other replicas served traffic. A new `schema_migrations` table records each file applied; a start runs only the missing ones, each in a transaction with its record. The first start of this version on an existing database runs every file once, as before, then records them all. `OBLETH_SCHEMA_VERIFY_ONLY=true` (Helm `obleth.schemaVerifyOnly`) applies nothing and refuses to start while a file is missing. Migration `0048` drops eight unused or redundant indexes, the unread `models.verifier_for` column, and the Postgres checks on `capacity_mode`, `capacity_source`, `endpoint_selection_mode`, replica `state` and knowledge document `status` (the gateway already checks those values; a stale check once failed saves). The active-batch count per key now names the tenant, so it reads an index. `schema/postgres/README.md` sets down how new schema files are written.
- **The crash guard reads one number per request, and capacity discovery lists each namespace once.** Every proxied request copied every discovered model's capacity status to read one model's ready count; the guard now reads that count (and the count of servers shutting down) directly, and the discovery metrics count states without a copy. A discovery pass listed EndpointSlices once per Service; when several wanted Services share a namespace it now lists the namespace once and splits the slices by Service (the same read the Service picker already makes, so the gateway's Role is unchanged).
- **Health checks probe a model's endpoints together, and model export reads endpoints once.** A model's endpoints were probed one after another, each with up to three attempts, so a large pool took the sum of every endpoint's latency; up to four are now probed at once, and the bulk check (`POST /api/v1/models/health`) runs four models at once instead of every model in turn. Model export read each model's endpoints with its own query, and import read them up to twice per model; both now read every endpoint in one query. `GET /api/v1/models/export` takes `?names=a,b` to export only those models (names that match no model are skipped); the dashboard's single-model export now asks for just that model instead of filtering the whole manifest.
- **The live fair-share view and the request log stop reading whole tenant, key and model tables for names.** `/fairshare/live`, which the dashboard polls every 2 seconds from each open tab, read every tenant and decrypted every model and endpoint on each call; it now reads only the names of the tenants and keys in its pools, and keeps the model and endpoint list for up to 15 seconds (a write on the same replica clears it at once). The request log, its facets and failure groups, and the per-model breakdown read every tenant row to label a page; all five now share one lookup of just the names, groups and key prefixes they show. A model enabled or disabled on another replica can take up to 15 seconds to show on the live view.
- **Indexing writes a document's chunks 500 at a time, and an upload is held in memory once.** Committing a document wrote its chunks one statement each inside the transaction, 6,000 round trips for a large document; they now go in as one statement per 500. An upload kept the base64 text, the decoded bytes and a copy of them as text at once; the text now takes over the decoded bytes and the base64 is dropped after decoding. Document reads no longer load the body: listing, uploading and reindexing returned every document's full text to code that never read it, and only the indexer's claim reads it now. Chunk texts are lent to the embedding requests instead of copied.
- **A batch claim reads only the items it takes, and one replica moves batches on per tick.** Claiming a batch's next items used an index ordered by retry time before line, so each claim read and sorted every due pending item of the batch; on a 50,000-line batch that was the whole batch, every few seconds, per runner. Postgres migration `0047` indexes pending items by batch and line, so a claim reads the 64 rows it takes, and drops the old index. Every replica also recounted every item of every active batch every 3 seconds; the tick now runs on one replica at a time, under an advisory lock, and recounts only batches with an item finished since their last progress (found through a second new index).

## v2.13.0

The review's first wave: usage reads share one bounded filter and agree on what a first token is, update bodies keep what they are not sent, the admin API refuses bad values instead of coercing them, the side endpoints and helper calls share one envelope and one set of limits, and the dashboard reaches every row of its long lists, says when a read failed, and passes the gateway's own errors through. No Postgres migrations; ClickHouse's daily rollup gains a column, applied when the gateway starts.

> **Upgrade notes.**
>
> - **The admin API is stricter.** A query parameter a usage read does not take is a `400` (`/usage` no longer accepts `group_by`); a bad `model_type`, `endpoint_selection_mode`, weight of 0, speculation threshold or energy setting is a `400` naming the field instead of being coerced; recipes answer `404` for a missing id, and `PUT /api/v1/recipes/{id}` no longer creates one. Inside the provisioner, replica state is a typed value instead of compared strings, and its gateway client has one create, one model lookup and one replica update where it had two, two and three.
- **One rule for update bodies: an omitted field keeps its stored value, `null` clears it.** `PUT /api/v1/keys/{id}` reset the weight, the caps and the budget it was not sent; `PUT /api/v1/models/{id}/reliability` zeroed `max_retries` when it was left out; `PUT /api/v1/models/{id}/endpoints/{endpoint_id}` re-enabled a disabled endpoint and reset its priority and weight when a body named only the fields it meant to change; and a model's own `max_in_flight` could never be lifted because `null` was read as "keep". Every field of those bodies is now optional and kept when omitted, `null` lifts a cap, a budget or an allowlist, and the OpenAPI description and CONTRIBUTING state the rule. Clients that send every field see no change; a client that relied on omission resetting a field must now send the value it wants.
- **A model is created in one statement.** Creating a model wrote the row and then switched it off, staged it, set its refused fields, its session affinity and its health-check interval in up to five more statements, none in a transaction, so a failure midway left an enabled, active model behind that the next resync would publish. The insert now carries every setting, and the store takes named `NewModel`/`ModelUpdate` structs instead of thirty-five positional arguments.
- **The Postgres pool is a setting.** Each gateway replica held exactly ten Postgres connections and waited sqlx's thirty seconds for a free one. `OBLETH_PG_MAX_CONNECTIONS` (default 10; chart `obleth.pgMaxConnections`) and `OBLETH_PG_ACQUIRE_TIMEOUT_SECS` (default 5; `obleth.pgAcquireTimeoutSecs`) set the pool size and how long a request waits for a connection before it fails instead of queueing behind the pool. Size Postgres `max_connections` for replicas times the pool plus the control plane.
- **Advice reads the ledger the way the request log does.** Advice's failure groups and per-model totals counted health probes and benchmark traffic, which every other usage read leaves out, so a benchmark that saturated a model could raise "waiting for room" or "platform failures" advice whose counts the linked request log did not show; both reads now exclude internal traffic, and Advice reuses the request log's failure-group query instead of carrying a copy. The Routing readiness card no longer repeats the long-answer warning: long answers are Advice's finding, with their evidence, and the card had shown the same model as a warning beside Advice's note.
- **obench reports true throughput for upstreams that omit usage, and its live dashboard stays out of the workers' way.** When a model server sends no usage object, obench estimated the answer's tokens from the whole SSE stream, framing included, which overstated output throughput by about 25 to 40 times; it now counts only the characters of `delta.content`. The stream is read one line at a time instead of being kept whole and parsed afterwards, and the live dashboard reads counters per frame and recomputes percentiles at most once a second from a copy sorted outside the lock the load workers need. The benchmark backend renders its token chunk once per stream and drops two unused dependencies. Earlier obench figures for upstreams without usage reports were overstated; do not compare them with this release's.
- **The scheduler forgets a quiet tenant on its own, and its quiet checks are constant-time.** A tenant that went quiet while ahead of its fairness clock was kept, with up to 512 idle keys, until its own next request or until the whole pool emptied; housekeeping (every 1 to 10 s) now reconsiders every quiet tenant and forgets it once the tenants still being served have moved the clock past it. Checking whether a key is quiet read every tenant's queue, and whether a tenant is quiet scanned every in-flight key; both now read counts kept as slots come and go (a key that moved between tenants still gets the full read), and a tenant over its idle-key bound sheds a batch of its smallest leads in one pass instead of rescanning per release.
- **Auto routing's fallback reads the request the way the classifier does.** With the classifier off, the heuristic that tags a request scanned the whole conversation, system prompt, replies and tool output included, so a system prompt that mentions code or a tool result with a stack trace tagged every later turn as coding at difficulty 2. It now reads the newest user turn with text (back three turns when the newest is empty), up to 8 KB, matches its keywords on whole words ("java" no longer matches "javascript", "bug" no longer "debug"), and takes the request's length from the token estimate. Images anywhere in the user's turns still mark the request as needing vision. Auto routing with the classifier off now picks cheaper tiers more often for long-system-prompt traffic. Sticky-routing keys are unchanged.
- **The admin API refuses a bad value instead of quietly changing it.** An unknown `model_type` was stored as `chat`, an unknown `endpoint_selection_mode` as `failover`, a tenant or group weight of 0 as 1, and an out-of-range speculation threshold or energy setting (a PUE below 1, a negative cost) was dropped while the request still answered 200. Each is now a 400 that names the field, like the quantization and key checks already were; the store no longer folds tenant, group or key weights. Scripts that relied on the old coercion see 400 where they saw 200.
- **A missing row is "not found" everywhere in the store, and recipes follow the admin conventions.** Store functions disagreed on what a missing row meant: some deletes answered success for an id that was not there (recipes, replicas), the knowledge store mapped the driver's row-not-found through its own helper, and two columns were read without a decode check. The rule is now one: a by-id delete of a missing row and a lookup or update of a missing id are `NotFound`, and every column read goes through the checked read. `DELETE /api/v1/recipes/{id}` answers 204, and 404 when there was nothing to delete (it answered 200 with a body either way); `PUT /api/v1/recipes/{id}` changes an existing recipe and 404s for a missing id instead of creating one (POST creates); the recipes endpoints carry their own OpenAPI tag.
- **The side endpoints open with one envelope, and search is admitted like every other request.** `/v1/search`, `/v1/audio/voices`, `/v1/load`, `/mcp/*`, `/v1/verdicts` and the job follow-ups each re-implemented the bearer check, the credential lookup, the key gates and the request-id header, and `/v1/search` ran a cut-down admission of its own (no background pool, no queue-wait header, no spans). One `authenticate_and_gate` and one `with_request_id` serve them all, so each refuses a missing token, a disabled key or an inactive tenant with the same status and body; one `admit` serves the pipeline, search and verdicts, so a search from a background key waits in the background pool, every search answer carries `x-obleth-queue-wait-ms`, and a traced search records its auth and admission spans. Jobs and speech build upstream URLs with one percent-encoder, the voices listing follows the model's endpoint selection mode and request timeout, and a listing over its 1 MB cap is refused instead of passed through cut short.
- **Every helper call is bounded and capped the same way, and a stalled speculation verifier ends the stream.** Helper calls (vision describer, structured repair, tool loop, image generation, MCP, tool streams, speculation drafts) each bounded their own time and reply size, or did not; the speculation verifier had neither, so a scorer that stalled after a draft was committed left the client's stream silent. One `with_timeout` gives every helper call a typed timeout the callers recognise by type, and one `post_json_capped` reads every helper reply under its cap. The verifier's calls are bounded by `speculation.verify_timeout_ms` (30 s) and capped by `speculation.verify_reply_max_bytes` (64 MB), both in Settings. Text helper calls (vision, structured repair) now record the cached part of their prompt in the ledger, as completion helper calls already did.

## v2.5.0

**Security**

- **Every method reads one spelling of a path.** Only POST paths were canonicalized. A `GET` or `DELETE` to `//v1/videos`, `/v1/v1/videos/{id}` or `/v1/./meshes/{id}/content` matched no job route, so it skipped the check that a job belongs to the caller and was forwarded to the backend, which lists and serves every job it holds; `POST /v1/./responses` skipped the Responses translation and its guardrails. Repeated slashes, a trailing slash and a repeated `/v1` prefix are now removed for every method before anything looks at the path, and a path with a `.` segment, or with a percent-escape of a letter, digit, `-._~` or a separator, is refused with 400.
- **Only inference endpoints are forwarded.** A request on any path, with any method, was forwarded to a model's upstream with the operator's key for it once its body named a model the caller could use, which reached whatever else that upstream serves: stored completions, files and fine-tunes at a hosted provider, a model server's management routes. The proxy now forwards `POST` to the endpoints it knows (chat, completions, embeddings, responses, audio, images, videos, meshes, rerank, moderations, score, tokenize, pooling, classify) and `GET` model discovery, and answers 404 `unknown endpoint` for anything else. Each forwarded endpoint requires a registered model, so a name the gateway does not have no longer reaches the default upstream. **There is no setting that opens other routes.** If your clients call a route of a model server that is not in this list, it now answers 404; an endpoint worth serving is added to the gateway, where it is admitted and metered like the rest.
- **Dashboard: changes must come from the dashboard.** The dashboard's API routes (`/api/live`, `/api/charo`, `/api/mcp`) accepted a POST from any page that the browser sent the admin's session cookie with, which includes pages on another port of the same host or on a sibling subdomain. They now refuse a change whose `Origin` is not the dashboard's own (or whose `Sec-Fetch-Site` is not `same-origin`). Requests that no page sent, such as a script with the cookie, are unaffected.
- **Dashboard: ids stay inside their path segment.** Ids and names from route parameters and forms were placed in Management API paths as they came, so a crafted one (`..%2F…`) reached a different admin endpoint than the one the route was for. Every one is now percent-encoded, and `.` and `..` are refused.
- **Dashboard: single sign-on never joins an existing account by email.** A sign-in through an identity provider was linked to an existing dashboard account when the provider reported the same, verified, email address. With a provider that vouches for an address its user chose, that signed the user in as the account's owner, the break-glass admin included. Implicit account linking is now off: an identity-provider sign-in is found again by provider and subject only.
- **Output guardrails read the whole answer.** A policy that blocks or redacts output read only the first choice's content and reasoning, and passed an answer on unread when it was larger than 4 MiB or not a completion. A caller could ask for two answers (`n: 2`), for token log-probabilities (which spell the answer out again, and make it large), or have the text come back as a tool call's arguments. Every choice is now read, with its refusal, legacy `text` and tool-call arguments; a redacted answer loses its log-probabilities; and an answer that cannot be read is refused with 502 instead of passed on.
- **A request the model has started on is not free to abandon.** A client that disconnected before the model server's first byte was billed nothing. With a non-streaming request that byte comes only once the whole answer is written, so closing the connection just before it made the work free, and a verdicts request was never billed on disconnect at all. From the moment a request goes to a model server, a disconnect is billed its prompt. A request the gateway fails or times out is still unbilled.
- **Input guardrails read a part's text whatever the part is called.** Only content parts of type `text` were scanned and redacted, so the same text in a part of another type (or none) reached the model unread.
- **Compression: a table that cannot be shorter is not built.** With the compression boon on a model, a message holding a list of objects that share no keys (`[{"k1":1},{"k2":1},…]`) was written out as a table of rows × columns empty cells before being found longer than the original: about 2.5 GB from 600 KB, before admission, for the whole gateway. The table is now skipped when its cells alone outweigh what it could save.
- **Sticky routing reads a prompt in one pass.** With the auto router's sticky sessions on, a message made of many `<think></think>` blocks took time that grew with the square of its length, on a request thread and before any budget check. Only the head of the text is used, and it is now read once.
- **`stream` must be true or false.** A request with `"stream": 1` was treated as not streaming, so the gateway did not ask the model server for usage, while a server that reads `1` as true streamed anyway and the answer was billed from the estimate. Such a request is now refused with 400. The output estimate also takes the larger of `max_tokens` and `max_completion_tokens` when a request carries both.
- **An MCP server is open only to the tenants named for it.** Any valid key reached every enabled server at `/mcp/<name>`, with the credential the operator saved for that server. Each server now has a list of tenants whose keys may call it directly (`allowed_tenants` on the Management API, "Tenants that can call it directly" in the server's panel), and the list starts empty. **Upgrading closes every existing server to direct calls** until you name tenants for it; such a call answers 403. Tools granted to a model are not affected, since the gateway makes those calls itself, and the dashboard's own checks still run.
- **MCP calls are limited per key.** One key may make 600 calls a minute to one MCP server; past that a call answers 429 with `Retry-After`. An MCP call carries no tokens, so no budget saw it before.
- **MCP servers at `/mcp/<name>`:** only the response headers MCP uses are passed back (content type, session id, protocol version, `WWW-Authenticate`, `Retry-After`, cache control), so a server cannot set cookies or grant cross-origin access from the gateway's address. A caller's cookies and forwarded-address headers are no longer sent to the server.
- **A tool call with non-ASCII arguments no longer ends the response.** Shortening a gateway tool's arguments for the progress line cut in the middle of a character when one sat at byte 120, which stopped that response.
- **The request log keeps 64 characters of an unknown `reasoning_effort`**, not the whole value, which could be megabytes and push a batch of rows over the size the log's write-ahead file takes.
- **Managed model scripts stay out of the audit log.** Saving a managed model wrote its preamble, launch command and script body to the audit log, which is searchable and never pruned. Each is now recorded as a line count.
- **Slack alerts** escape `&`, `<` and `>` in the text they quote, so a model name in a request cannot add a link or a mention.
- **Dependencies:** `rustls-webpki` 0.103.16 and `webpki-roots` 1.0.11 (stop trusting two intermediate certificates whose keys are public), `rustls` 0.23.46, `tokio` 1.53.3, and the `zod` inside the dashboard's sign-in library to 4.6.7.

**Gateway**

- **Live load per model.** `GET /v1/load` on the proxy port tells a client how busy each model it can use is right now, so it can show that a model is busy or full and say why a request is waiting. It takes the caller's key or identity token like `/v1/models`, and lists the same ids. Each entry has the model pool's `slots`, the requests `in_flight` in it and `waiting` for it, and a `state`: `free`, `busy` (at least 80% of the slots in use), `full` (every slot in use, or anyone waiting) or `offline` (no servers). A variant reports its model's pool and a family its default member's. `scope` is `cluster` when the counts cover every gateway replica and `replica` when they are the answering replica's own. When the caller's key or tenant has an in-flight cap, each entry also has `you`: the caller's own requests in flight in that pool, and the tighter of the two caps as `limit`, which holds in each pool separately. `?model=` returns one entry. The numbers are the ones the Fairshare page shows, read at most once a second per replica however many clients poll, and the answer names no other tenant or key.
- **Tool calls keep their arguments when a tool is marked `strict`.** The gateway removes the `strict` flag from each function tool before the request goes upstream. vLLM does not enforce it as a schema guarantee, and with some models' tool parsers it made calls drop their string arguments, such as the code in an edit tool's `old_str` and `new_str`. Agent frameworks set the flag by default, so those models failed at editing files through the gateway. Only the per-tool flag is removed: the schema, `response_format`, and everything else are sent as before. `/v1/responses` and `/v1/messages` already left the flag out.
- **Energy in the response.** When energy accounting measured a chat or text completion, its `usage` also carries `energy_wh` and `co2_g`: in the JSON body, or in the usage chunk of a stream that asks for one with `stream_options.include_usage`. An answer that ran the gateway's tools (image generation, web search, MCP) or a speculation draft carries the energy measured for the whole request. They are read as the answer ends, a moment before the request settles, so they can differ from the stored figures in the last digits. A request with nothing measured, a cache hit, and every request while energy accounting is off answer exactly as before.
- **About 40 ms less per request on kept-alive connections.** The proxy, admin and metrics listeners now set `TCP_NODELAY` on every connection. A response goes out as headers, then body. With Nagle's algorithm on, the body waited for the client to acknowledge the headers, and on a reused connection Linux delays that acknowledgement by up to 40 ms, so most requests through a proxy or a pooling client took that long extra. New connections and `curl` were not affected.

- **Batches.** The OpenAI Files and Batches APIs: upload a JSONL file of requests to `/v1/files` with purpose `batch`, create a batch from it at `/v1/batches`, and collect the output and error files when it finishes. Existing OpenAI clients work unchanged. Batches accept `/v1/chat/completions`, `/v1/completions` and `/v1/embeddings`, one model per batch.
  - **Background priority:** batch requests run through the ordinary pipeline (routing, guardrails, boons, budgets, the usage ledger) as the batch owner, in a background pool per model. A batch request starts only while no interactive request waits for the model on any replica (a slot freed while one waits goes to it, never to batch work that asked first), and background work fills at most `OBLETH_BATCH_MAX_SHARE` (0.75) of the model's slots and of the global ceiling, so interactive arrivals always find the rest free. Nothing in flight is interrupted. Batch owners share the background pool by the same group, tenant and key weights, and background work never counts against anyone's interactive caps. Across replicas the share holds cluster-wide through the shared slots.
  - **Runner:** every replica claims items with a lease, keeps a few waiting per batch owner and model beyond those running (so fairshare weights decide between owners), retries 429, 5xx and timeouts with backoff up to `OBLETH_BATCH_MAX_ATTEMPTS` (5), and claims again as soon as an item finishes. A replica that shuts down stops claiming, finishes its running requests during the drain and hands back the rest at once; one that dies has its items back in the queue within a minute, when their lease lapses. A disabled key or inactive tenant pauses its batches instead of failing them. Batch counts are recomputed from the requests every few seconds, so a status poll can lag by up to 3 s.
  - **Lifecycle:** each line is checked when the batch is created, and a batch with bad lines fails at once with the line numbers. `completion_window` accepts `<n>h` or `<n>d` from `OBLETH_BATCH_WINDOW_MIN` (1h) to `OBLETH_BATCH_WINDOW_MAX` (7d); requests still queued at the deadline are written to the error file as `batch_expired`. Cancel stops queued requests and lets running ones finish. Batch objects carry the standard fields plus an `obleth` object with the model, the deadline, `last_progress_at` (when a request last finished) and `waiting`: `capacity` when the batch has requests left and none has finished for two minutes, usually because the model is busy with interactive work.
  - **Results so far:** `GET /v1/batches/{id}/results` streams the output file's lines for the requests finished so far, while the batch still runs as well as after; `?errors=true` streams the error file's. Same format as the files.
  - **Delete:** `DELETE /v1/batches/{id}` removes a batch that has stopped, with its requests, answers, output and error files, and its input file unless another batch read it too. A batch still running gets 409 `batch_running`: cancel it first.
  - **Dashboard:** a Batches page (Operations) lists every tenant's batches with a progress bar, who submitted each, its model and what it is doing in plain words (running with the time left at its pace, waiting for capacity, done with failures, ran out of time), refreshing every few seconds while any runs, and cancels one. The admin API behind it: `GET /api/v1/batches` (filters `status`, including `active`, `tenant_id` and `model`; counts by status), `GET /api/v1/batches/{id}` and `POST /api/v1/batches/{id}/cancel` (audited as `cancel_batch`).
  - **Storage and limits:** files, batches and one row per request in Postgres (migration `0039`). Uploads are stored in 4 MB chunks as they arrive and read back the same way, so a gateway's memory does not grow with file size. Output and error files are read from the request rows when downloaded. An upload over the size limit is refused with 413. Defaults: 50,000 requests and 200 MB per file (`OBLETH_BATCH_MAX_LINES`, `OBLETH_BATCH_MAX_FILE_BYTES`), 10 active batches per key (`OBLETH_BATCH_MAX_ACTIVE_PER_KEY`), 64 batch requests in flight per replica (`OBLETH_BATCH_RUNNER_CONCURRENCY`), 30 days retention (`OBLETH_BATCH_RETENTION_DAYS`). Files and batches are private to their key by default (`OBLETH_BATCH_SCOPE=tenant` shares them across the tenant).
  - **Usage:** ledger rows for batch requests have `request_type` `batch`.

**Deployment**

## v2.4.0

Session affinity and the derived session id fix below follow the design @summerisgone proposed in #83. Thank you!

> **Upgrade notes.** No breaking changes. Postgres migration `0038` only adds a column, and the gateway applies it when it starts. Session affinity and sticky `auto` routing are both off until they are configured. With session affinity off, v2.3.0 and v2.4.0 replicas can share slots during a rolling update; turn it on once every replica runs v2.4.0.
>
> - **Behaviour to expect after upgrading:**
>   - Derived session ids change once for conversations whose system prompt and first user message together were longer than 8 KiB. Those conversations get their own ids instead of sharing one, so the request log groups them apart and `session_hash` routing spreads them across endpoints. Shorter openings hash exactly as before.
>   - OpenAI's `prompt_cache_key` is read as a session id when the request has no `session_id` or `metadata.session_id`. Clients that send it are grouped into sessions by it and, under `session_hash`, kept on one endpoint per key.
>   - Responses to `auto` carry `x-obleth-auto-model`.

**Gateway**

- **Session affinity** (off by default). Agents send a session's steps one after another over a growing prompt, and when capacity is short a step that waits behind other sessions often finds its prefix evicted upstream and is prefilled again from scratch. With affinity on, each model pool favours sessions that are still warm.
  - **Ordering:** a session with a step running, or whose last step finished within `OBLETH_FAIRSHARE_SESSION_AFFINITY_WARM_SECS` (120), goes ahead of older requests from the same key. Which tenant and key is served next is still the fairshare decision.
  - **Held slots:** when a step that arrived within `..._HOLD_MS` (3000) of the session's previous step finishing is done, its slot is held for that long for the session's next step. A held slot counts against the pool, the global ceiling, the tenant and the key like a running request, so it never lets anyone past a cap or a share, and it is billed to the step that takes it.
  - **Bounds:** at most `..._MAX_HELD_PERCENT` (25, rounded up) of a pool's slots are held at once. A queued request is passed by later requests of its key at most `..._MAX_JUMPS` (8) times; then it goes next and its key holds nothing until it is served. Once a request has waited `..._MAX_BYPASS_SECS` (30) on any replica, its pool's held slots are freed and no new ones are held until it is served. Holds give way only to queued requests a free slot would actually go to.
  - **Across replicas:** in shared slot mode holds live in Redis, so a session's next step takes its held slot on whichever replica it lands. New keys: `obleth:fairshare:hold:<id>`, `obleth:fairshare:holds`, `obleth:fairshare:recent` and `obleth:fairshare:chain`, plus `h|<pool>` and `wa|<pool>` fields in the totals hash. A hold nobody takes is freed when it runs out, the way a dead replica's holdings are.
  - **Scope:** sessions are the client's or the derived session id, scoped to the scheduler key, and only models that send a session to one upstream take part (any endpoint selection but `load_balance` across several endpoints).
  - **Per model:** a model's `session_affinity` turns it on or off whatever the gateway default, and can set its own `hold_ms` (up to 60000), `max_held_percent` (0 to 100) and `max_bypass_secs` (1 to 3600). Anything left out uses the gateway's values, which are read even while the gateway default is off; `{}` (the default) follows the gateway. Set it with `PUT /api/v1/models/{id}/session-affinity` or the field on model create and update. It is stored in Postgres (migration `0038`) and carried in manifests (exported only when set) and backups. A model that turns affinity off gives back the slots its pool held.
  - **Metrics:** `obleth_fairshare_held_slots` and `obleth_fairshare_affinity_total{event}` (`jump`, `hold`, `redeem`, `expire`), and each pool in the fairshare snapshot reports `held`.
- **Sticky `auto` routing** (off by default). With `sticky_enabled` in the routing settings, a conversation stays on the model that answered its last turn and moves up a level only on evidence the model is not doing a good job:
  - the client sends the same request again after it was answered;
  - the classifier reads the user's newest message as reporting the last answer as wrong (one more single-token question, asked only on follow-up turns);
  - the last answer was broken: no content and no tool call, or tool-call arguments that are not JSON;
  - the model made the same tool calls three turns in a row, or two tool turns in a row came back with errors.
  
  A move up raises the conversation's floor one level and leaves the incumbent out. A harder turn raises the floor to its difficulty, and the level never drops. On a topic change the incumbent stays when it holds a level in the new topic at least the turn's difficulty. When the incumbent cannot take a request (down, too little context, a missing capability, no longer allowed) the turn goes to another model at its level or above. The first turn routes as before.
  
  The gateway keeps no conversation id and stores none of the conversation's text: after a turn it records the model and level in Redis (`obleth:auto:`, two-hour expiry) under a hash of the user message and the answer, and the next request finds it by hashing its last assistant message. Responses carry `x-obleth-auto-reason` when stickiness is on, `obleth_auto_routes_total{model,reason}` counts picks, and the `auto_route` trace span records the decision.
- **Derived session ids** give the first user message an 8 KiB budget of its own after the system and developer text. A client whose system prompt alone filled the old shared cap had every conversation of a tenant hashed to one id. `prompt_cache_key` is now read as a client session id (see the upgrade notes).
- **Model speed API.** `GET /api/v1/usage/speed` returns each model's median and slowest-tenth output tokens a second, first token and prompt speed, for a window or per hour or day cut in the caller's time zone (`bucket`, `tz`), filtered by tenant, key or model. It counts only successful, uncached requests that produced tokens, with the same decode rate as `/usage/models`.

**Dashboard**

- **Reports → Model speed:** one row per chat model with a square per day (or hour, over a day or two), shaded by how that period compared with the model's own usual speed, so a slowdown shows whatever the model's speed. Opening a model shows its median, slowest tenth, first token and prompt speed, a sentence on how its speed went, and a chart aligned with the squares. Models with too few requests to judge sit behind "show more".
- **Models → Capacity → Session affinity:** Gateway default, On or Off, with the hold time, held share and wait limit shown while it is On (blank uses the gateway's).
- **Settings → Routing:** a switch for sticky `auto` routing.
- Next.js 16.4.2 and React 19.3.1, which pick up the Next.js 16.4.1 security fixes (image optimization for SVGs, `use cache` functions returning typed arrays, and a Server Actions denial of service).

>
>   An external ClickHouse (`clickhouse.enabled: false`) is not changed. Set the same retention on it yourself.
> - **Behaviour to expect after upgrading:**
>   - Requests appear on the Logs page up to 5 seconds after they finish. Budgets are not affected.
>   - On `/v1/messages`, when the upstream reports cached prompt tokens, `input_tokens` is now the uncached part and the cached part is `cache_read_input_tokens`, as Anthropic defines them.
>   - Models added in the dashboard, or launched from a recipe, start **staged**: they answer by name but are not listed or picked by `auto` until made active. Models created through the Management API without a `status` still start active.
>   - Router readiness warns until an auto-eligible model carries the new `writing` tag.
> - **Slurm:** the shipped recipes take the model cache folder, setup commands and container images from the new **Cluster defaults** on the Slurm connection, and a launch is refused while one it needs is unset. Fill them in before launching from the library.

**Gateway**

- **Models have a lifecycle: staged, active, deprecated and retired.** `PUT /api/v1/models/{id}/status` sets it, and a model's page has a Lifecycle section that previews what callers will see and lists the keys that called the model in the last 30 days.
  - **Staged:** the model answers anyone who sends its name, but nothing advertises it. It is left out of `/v1/models`, `/model/info` and `/v1/search/tools`, `GET /v1/models/{id}` returns 404, and `auto` never picks it. Health checks and capacity discovery run as usual, so you can see it working before it goes live. `POST /api/v1/models` takes `"status": "staged"`, and the Playground can still call it.
  - **Deprecated:** served as usual. Every response carries `Deprecation` (RFC 9745), `Sunset` (RFC 8594) once a retirement date is set, a `Link` to the replacement with `rel="successor-version"`, and `x-obleth-model-status` and `x-obleth-model-replacement` for people reading headers. `auto` stops picking it. Listings show its status, replacement, retirement date and note.
  - **Retired:** refused with `410 Gone` and an error (`code: model_retired`) that names the replacement and the date. With `redirect` on, the replacement answers instead and the response carries `x-obleth-redirected-from`. A deprecated model retires on its own once its `retire_at` passes. Refusals are logged, so the request logs show who still calls it. Retired models are left out of listings, health checks and capacity discovery.
  - The check runs on every proxied endpoint, `/v1/verdicts` and `/v1/search`, after aliases and variants are resolved. The models list shows Staged, Deprecated and Retired badges, and the tenant portal leaves staged and retired models out. Backups carry the lifecycle; an older backup restores every model as active.
- **Web search, on its own endpoint and as a boon.** A search tool is a model of type `search` whose `api_base` is a SearXNG instance ("Web search (SearXNG)" in the type picker).
  - **`POST /v1/search`** (or `/v1/search/{tool}`) answers in the Perplexity Search API shape that LiteLLM's `/v1/search` uses, so clients written for it work unchanged. `GET /v1/search/tools` lists the tools a caller may use. A request takes `query`, `max_results` (1–20), `search_domain_filter` and SearXNG's own options. A search goes through key auth, the tenant's model allowlist, input guardrails and fairshare admission like a model call. It costs nothing and is logged as `search`. Search tools are not models: they are left off `/v1/models`, and a chat call that names one gets a 400.
  - **The `web_search` boon** gives a chat model a `web_search` tool. The gateway runs each search through the tool picked in Settings → Boons → Web search, and the model is told to cite the URLs it uses. The defaults are 5 results per search and 3 searches per request (at most 10 and 8), with 15 seconds per search. The boon fails open: a missing tool, an upstream error or the limit becomes a short tool result, never a failed chat. A client that brings its own `web_search` tool keeps it. Each search is a free usage row linked to the chat request.
  - **The Playground has a Search mode** to try a search tool, with Get code for curl, Python and JavaScript.
- **Tool boons follow Function calling.** Image generation and Web search give the model a tool to call, so the gateway adds them only to models flagged for function calling. The dashboard now refuses to switch them on while Function calling is off, and turning Function calling off turns them off, as it already did for MCP tool grants. A grant saved earlier stays and is marked as doing nothing. The model overview and Settings → Needs you flag such models.
- **Model variants: opt-in names with extra boons.** A model can list up to 8 variants: names for the same model with more boons on, for example `my-model-spec` for `my-model` with speculation. Someone who asks for the model by name still gets the model's own output. A variant shares its model's pool, capacity, prices and upstream, is listed in `/v1/models` with `variant_of`, is never picked by `auto`, and keeps its own response-cache entries. Responses carry `x-obleth-model-variant`, plus `x-obleth-drafted-by` when speculation released a draft. Variant names share one namespace with model names and aliases, so creating a model under another model's alias or variant now returns 400.
- **Helper calls are linked to the request they served.** A boon's helper calls (speculation drafts and checks, vision, structured-output repair, guardrails, tool loops, image generation and web search) used to show up as separate usage rows under the helper model's name, so people found models in their usage that they never called. Usage rows now carry `parent_request_id`, and the client's own row records `model_variant`. The request log filters by `?parent_request_id=`, and the request panel lists each helper call in plain words and links back. Per-model reports and the daily rollup are unchanged.
- **Per-end-user fairshare for a key that fronts many people.** A shared front end sends all its users through one key, so one busy user held up everyone else on it. With the new per-key switch on (Per-user fairshare in the key panel, or `PUT /api/v1/keys/{id}/end-user-fairshare`), a request names its end user in an `x-obleth-end-user` header or the body's `user` field (Anthropic's `metadata.user_id` counts), and each user queues as if they held their own key, with the key's weight and in-flight cap. Budgets, usage and cost stay on the key, and requests that name no one share one place as before. The switch is off by default and only an operator can set it, because a caller could otherwise split itself into many users to jump the queue. The header is not forwarded upstream, and the ledger records the user in a new `end_user` column.
- **Cached prompt tokens on every API, and in the ledger.** An upstream with prefix caching reports how much of each prompt it served from cache (vLLM does when started with `--enable-prompt-tokens-details`). The gateway now records it as `cached_input_tokens` and reports it on the Responses API (`input_tokens_details.cached_tokens`) and the Messages API (`cache_read_input_tokens`), not only on chat completions. The request detail shows Cached input tokens. The ledger's `input_tokens` still counts every prompt token, so totals and prices keep their meaning.
- **The vision boon reaches the models it is for, and never forwards an image raw.** The Playground now sends images to a text-only model that has the vision boon, while the boon is on with a describer set. When an image can't be described (the describer times out, fails or isn't set, or the image is past `max_images`), the model gets a short note saying so in its place. The model answers instead of the request failing as "not a multimodal model".
- **A `writing` routing tag for prose to draft or edit.** `creative` reads as fiction and verse, so "tighten this paragraph" or "make this email more diplomatic" had no topic tag and no model could claim them. `writing` covers them, and the keyword fallback learns it too. "Write" is also the verb of code requests, so `coding` and `writing` are an exclusive pair: when both score, the weaker is dropped and its place goes to the next tag.
- **A new classifier model doesn't inherit the old one's answers.** The auto router cached classifications by prompt alone, so after the classifier model changed, the old model's answers kept being served for up to the cache's 5 minutes, including empty results cached after a failure. The cache key now includes the classifier model.
- **Fairshare slot totals count only models that have servers.** A model with nowhere to send a request (no `api_base` and no endpoint, or a discovered model with no ready replica) keeps its pool size for admission, but no longer adds to the capacity totals in `GET /api/v1/stats` and `GET /api/v1/fairshare/live`. The live view lists such models in `models_without_servers`, and the Fairshare page shows them as No servers.

**ClickHouse, telemetry and the chart**

- **ClickHouse keeps a week of its own logs, not all of them.** The bundled ClickHouse ran the stock config, which logs at trace and keeps its system log tables (`query_log`, `part_log`, `metric_log`, `text_log`, …) forever. On a busy gateway they outgrow the usage ledger many times over and can fill the chart's 20 GiB volume, and a full disk stops usage inserts. The chart now mounts a config that partitions each of those tables by day and drops days older than `clickhouse.systemLogRetentionDays` (default 7). The server logs at `clickhouse.logLevel` (default `information`), and `text_log` keeps warnings and errors only. Changing either value restarts the ClickHouse pod. The Compose files mount the same settings from `deploy/docker/clickhouse/system-logs.xml`.
- **Usage is written to ClickHouse every 5 seconds, not every second.** Each gateway replica inserted a few rows about once a second, and ClickHouse rewrote every small insert in later merges: on one install, 55 GB a day of merge writes for a 24 MB usage table. `OBLETH_TELEMETRY_FLUSH_INTERVAL_MS` (Helm `obleth.telemetryFlushIntervalMs`, default 5000, clamped to 100–60000) sets how long each replica buffers usage rows and trace spans. A full buffer still flushes at once, shutdown still drains everything, and write-ahead replay keeps its one-second pace.
- **`kubectl port-forward` reaches the dashboard.** Next.js binds to `$HOSTNAME`, which Kubernetes sets to the pod name, so the dashboard listened only on the pod IP and a port-forward to it never connected. The chart now sets `HOSTNAME=0.0.0.0` on the dashboard container, as the Compose file already did.

**Deployments on Slurm**

- **A new deployment starts from the model and shows every job setting.**
  - **Pick what to run:** your saved recipes, the shipped library, or a Hugging Face repo id. For a repo, obleth reads its files and config (architecture, format, quantization, size, licence, gating) and lists the engines that can run it.
  - **Where and how it runs:** every field the launcher sends, on one form or as YAML. That covers partition, account, QoS, walltime and nodes, GPUs, CPUs and memory per node, required node features, nodes to avoid, job logs and environment. Each value says where it came from: the recipe, a cluster default, past launches, or your change. The YAML is checked line by line against the recipe's inputs and what slurmrestd reports, and the form offers only the accounts the chosen partition accepts.
  - **Review** shows the rendered script and what goes to Slurm, and can save the settings as a recipe. A serving deployment can be saved as a recipe too, and values left at the cluster default stay as references.
- **Past launches suggest what to change.** A launch history keeps one row per replica, after the replica, spec and model are gone (`GET /api/v1/deployments/launches`). Each row has the spec, the nodes, the timings and how the job ended in Slurm's own words (`TIMEOUT`, `OUT_OF_MEMORY`, `NODE_FAIL`, …). The form uses it to fill in account and QoS when recent launches agreed on them. It also suggests a longer walltime after timeouts, more nodes after running out of memory, or avoiding a node whose launches keep failing, and it shows queue wait and time to healthy. Each suggestion shows its evidence, and nothing is applied unless you pick it.
- **Recipes have typed inputs, cluster values, and a record of where they ran.**
  - `inputs:` entries are text, choice, number, path or flag, with help, limits, options, a unit, the flags a flag adds, and defaults per node count; `variables:` still works. An optional input left empty adds nothing to the script.
  - `{{cluster.cache}}`, `{{cluster.images}}`, `{{cluster.image.<engine>}}`, `{{cluster.logs}}` and `{{cluster.setup}}` come from the new Cluster defaults tab on the Slurm connection. An image name there can include `$(uname -m)` for clusters with both Arm and x86 partitions. The connection also stores a Hugging Face token, encrypted, which jobs get as `HF_TOKEN` and `HUGGING_FACE_HUB_TOKEN` in their environment, never in the script.
  - A flag input can declare `capabilities:` (`function_calling`, `tool_choice`, `response_schema`, `vision`), and a launch creates the model with them. The shipped recipes with a Tool calling flag declare function calling and tool choice, so their tool boons work without a second step.

The library now has 16 recipes, each run and served on a single A100, H100 or GH200 GPU: chat, embedding and transcription models, two smoke tests, and one starting point per engine (vLLM, SGLang, llama.cpp and Ollama). A test keeps untried recipes out. `qwen2.5-0.5b` is now `smoke-test-ollama`.
- **Slurm launches work on real clusters.**
  - **The job environment reaches the job.** The provisioner now sends it as a list of `NAME=value` strings, the format slurmrestd v0.0.39 and later expect. Before, slurmrestd dropped it, so `PATH` and `HF_TOKEN` never arrived.
  - **Scripts are submitted with Unix line endings.** A script edited in the dashboard was saved with Windows line endings, and bash failed on its first line. Scripts already stored are fixed when they are submitted.
  - **A memory of 0 gets the whole node.** It used to be dropped, which gave the job the partition's default. Some sites' `job_submit` plugins read 0 as unset, so the provisioner sends the smallest node's real memory minus its reserved memory instead, and falls back to 0 when it can't read the nodes.
  - **`#SBATCH` lines move to Placement.** slurmrestd ignores them in a script. A launch now keeps their values in the job settings, and a deployment whose script still has them offers **Move them to Placement**, saying how each differs. Placement labels GPUs, CPUs and memory, and says in a sentence what each replica asks Slurm for.
  - **Refusals and failures are easier to read.** When Slurm refuses a job, the deployment page leads with Slurm's own sentence and what to change. A deployment's **Job logs** folder collects each job's `.out` and `.err`, and when a deployment stops, the page says where the last job's output is. A lost replica records how its job ended.

**Gateway**

- **Verdicts: typed decisions instead of generated text.** `POST /v1/verdicts` takes a state (a string or JSON) and a map of typed questions (boolean, choice of up to 26 options, or a score over 2–10 ordered levels) and returns one verdict per question with its probability distribution and a confidence. Each question is one greedy single-token call to the route's own chat backend with `top_logprobs`; the first-token distribution over fixed answer labels is renormalized, and mass outside the labels lowers confidence instead of corrupting the answer, so a verdict cannot come back malformed. Questions fan out concurrently against one pinned endpoint with a byte-identical prompt prefix, so with prefix caching each extra question costs about one cached prefill and one token. Requests run the full pipeline (one fairshare permit, budgets, usage as request type `verdict`, a trace span per question). Thinking models are retried past an empty think block and harmony (gpt-oss) models through a completions prompt already open in the final channel, and each model's working variant is remembered; a degenerate 200 or one transient 5xx gets one retry, and failures name the resolved model. Floats are written as plain decimals at full precision. The Playground has a Verdicts mode.
- **Fairshare is per model, and fair inside a tenant.** Every model now has its own scheduling pool (32 slots by default, or the model's max in flight), so a saturated model no longer delays a model with free capacity and usage on one model no longer costs a tenant priority on another. Inside a tenant, keys are served by weight: each key has a fairshare weight (default 100) and an optional per-model in-flight cap, so one user cannot starve their team. The per-tenant max in flight is now enforced, per model. The fairshare page gains a model selector and shows each tenant's keys; the live API reports per-pool detail alongside the aggregated view. `OBLETH_GLOBAL_MAX_IN_FLIGHT` is now a total ceiling across pools (default 4096) and `OBLETH_DEFAULT_MODEL_MAX_IN_FLIGHT` sets the default pool size. Upgrading: a deployment that pinned `OBLETH_GLOBAL_MAX_IN_FLIGHT` (the shipped compose file used 64) should raise it above the sum of its models' pool sizes — otherwise the ceiling binds before the pools do, and the gateway logs a warning at start-up.
- **Fairshare limits hold across replicas, and any replica can use the whole of them.** With more than one gateway replica live, every pool size, per-tenant and per-key max in flight, and the global ceiling is a set of cluster-wide slots in Redis (`OBLETH_FAIRSHARE_SHARED_SLOTS`, default on; Helm `obleth.fairshareSharedSlots`). Each replica keeps its own fair queue and picks the next waiter as before, then admits it only after one Redis script call has taken a slot against the configured, undivided limits, checking the pool, the ceiling and the tenant's and key's caps together; finishing the request gives the slot back in one call. A model with 20 slots behind 3 replicas therefore admits all 20 requests on whichever replica they reach, instead of capping each replica at 7 and leaving one queueing behind long streams or keep-alive connections while the others sit idle, and never admits a 21st anywhere. A tenant capped at 10 gets 10 across the fleet. With a single live replica there is no Redis call on the request path. Replicas heartbeat into Redis (every `OBLETH_FAIRSHARE_REPLICA_HEARTBEAT_SECS`, default 5; live for `OBLETH_FAIRSHARE_REPLICA_TTL_SECS`, default 15), and Redis records what each replica holds: a replica that crashes has its slots reclaimed by the next live replica's heartbeat once its own expires, never before, and one that shuts down cleanly gives back anything left after draining. Every heartbeat interval each replica re-asserts its true holdings, which repairs the count after a lost release. When a slot frees while someone waits for it, Redis publishes the pool on a channel and the replicas waiting there each retry once; a randomized 100–250 ms retry covers a lost message. Fairness is exact within a replica; across replicas a freed slot goes to whichever claims it first. If Redis fails or answers slower than its response timeout, a replica falls back to the split and logs once, then reconciles its holdings and returns to shared slots when Redis answers; it never admits without a limit. The split is `OBLETH_FAIRSHARE_REPLICA_AWARE` (default on; Helm `obleth.fairshareReplicaAware`): each replica enforces the configured value divided by the live replica count, rounded up and never below 1. It applies whenever shared slots are off or unavailable; with it off too, each replica enforces the full limits. Changing mode or replica count resizes pools live without cutting in-flight requests short. `GET /api/v1/fairshare/live`, `GET /api/v1/stats` and `GET /api/v1/capacity/discovery` report the replica's `mode` (`shared`, `split`, `fallback` or `local`), the live replica count, and in shared mode the cluster-wide in-flight count overall and per pool next to the replica's own; the Fairshare page reads "In flight 12 of 20 (cluster-wide, 3 gateways)" with this gateway's count beside it and flags fallback, and the model's Capacity section shows its cluster-wide occupancy. Prometheus gets `obleth_fairshare_replicas`, `obleth_fairshare_shared_slots_mode{mode}` and `obleth_fairshare_cluster_in_flight`. The start-up ceiling check compares the configured ceiling with the configured pool sum, and each replica's share of both when the limits are divided.
- **Pool sizes that follow the backend (`discovered` capacity mode).** A model in the new `discovered` capacity mode takes its fairshare pool size from its live backend instead of a typed-in `max_in_flight`: the ready serving replicas' concurrency summed, × `capacity_headroom`, rounded up and never below 1, so the gateway's limit tracks the backend's own autoscaler. Replicas are counted by the model's `capacity_source`: `endpoints` (the default) counts the model's enabled, healthy endpoints (only the one in use under `failover`; a model with no endpoint rows counts its `api_base` while healthy) and needs nothing outside the gateway, which suits Docker, bare metal and external providers alike; `kubernetes` counts the ready, serving, non-terminating endpoints of a Service, read from its EndpointSlices and de-duplicated across slices. Only replica counts are read, never pods. The per-replica concurrency is the operator's, set once: the model's `per_replica_max_in_flight` (e.g. your server's max concurrent sequences, such as vLLM `--max-num-seqs`), so the sum is ready replicas × that value; for `endpoints`, each ready endpoint counts at its own new `max_in_flight`, or the model's value when it has none, and the values are added up (endpoints at 8 and 2 and one unset with a per-replica value of 4 make 14). It is required for the `kubernetes` source, and for `endpoints` unless every endpoint sets its own; a write without it is refused with a message saying what to set. A kubernetes model names its Service with `capacity_service` (unset uses the `OBLETH_CAPACITY_DEFAULT_SERVICE` template with `{upstream_model}`/`{model_name}` placeholders, empty by default, so such a model needs its own Service; a rendered name that is not a valid Service name refuses the model) and its `capacity_namespace` (unset looks the Service up in each allowed namespace in order, and the first one that has it wins). Which pods count is the Service's own selector, so a multi-node deployment where only some pods take requests points the model at a Service that selects just those. Every gateway replica reads the sources on its own every `OBLETH_CAPACITY_DISCOVERY_INTERVAL_SECS` (default 15; one EndpointSlice list per distinct namespace and Service, served from the API server's cache) with no database writes, and hands the result to fairshare as the model's configured, cluster-wide pool size, enforced across the gateway replicas like any configured size; a change resizes the pool without cutting in-flight requests, and growth admits waiters at once. When a source has no serving replica, the Service is not there, or the source does not answer, the last derived value holds (or the static `max_in_flight`/default if there is none yet); a model that cannot be discovered as configured (no Service, a namespace outside the allowlist) uses its static value; each state change is logged once. A cap at 100% of ready capacity still lets an autoscaler that scales on backend utilization or running requests see saturation; one that scales on queue depth needs requests to queue at the backend, which `capacity_headroom` above 1 allows. Discovery is off unless `OBLETH_CAPACITY_DISCOVERY_ENABLED` is set, and the kubernetes source additionally needs `OBLETH_CAPACITY_DISCOVERY_NAMESPACES` and read access to EndpointSlices there; a kubernetes model whose namespace is outside that list, or that has no Service, is refused when it is written. `GET /api/v1/capacity/discovery` reports each discovered model's source, Service and the namespace it was found in, ready replicas, per-replica value and whether it is configured or per endpoint, derived and effective pool size, the size the answering replica enforces with its own and the cluster-wide in-flight count, last refresh and the reason when it is not discovered; `obleth_capacity_discovery_models{state}` counts them by state. In the dashboard, the model's Capacity section offers `discovered` next to `static` and `tuned`, edits the source, the required per-replica concurrency and headroom, and shows the answering replica's discovery state with the live `ready × per replica = limit`. The Service is picked rather than typed: when a Service in the allowed namespaces matches the model's default, the tab confirms it ("Using `<service>` in `<namespace>` · N ready", with Change); otherwise, or on Change, a searchable list of the Services the gateway sees ("service · namespace · N ready") sets the Service and namespace together, and "Use default" clears both. The list comes from the new `GET /api/v1/capacity/services`: every Service in the allowed namespaces with its ready endpoint count, grouped from the same EndpointSlice lists discovery reads (no new permission), cached for 15 seconds, with the reason when it is empty (discovery off, no namespaces, a namespace refused); `?model=` adds the Service that model would use by default and the namespace it was found in; the endpoint list shows and sets each endpoint's max in flight. The fields are settable on model create and update, the capacity-mode endpoint, manifests and backups. Helm: `obleth.capacityDiscovery` (`enabled`, `intervalSecs`, `namespaces`, `defaultService`, all off or empty by default); only when discovery is on and namespaces are listed does the chart render a gateway ServiceAccount and, in each listed namespace, a Role limited to get/list/watch on `endpointslices` (`discovery.k8s.io`) with its RoleBinding: nothing on pods, Services or Secrets and no ClusterRole, so the permission reveals only Service endpoint addresses and readiness. `examples/values-capacity-discovery.yaml` shows the settings. Compose passes the settings through, off. Migration 0029 is idempotent.
- **The global in-flight ceiling defaults to 4096.** With per-model pools doing the limiting, `OBLETH_GLOBAL_MAX_IN_FLIGHT` is a safety cap, and the earlier default of 1024 sat below the sum of pool sizes on a fleet of more than 32 default-sized models, which logged the start-up warning and let the ceiling bind first. The code default, the Helm value `obleth.globalMaxInFlight`, and the compose file now use 4096. A deployment that set its own value keeps it.
- **The fairshare activity chart keeps an hour of history.** The gateway samples the scheduler every 2 seconds into memory (`OBLETH_FAIRSHARE_HISTORY_SECS`, default 3600; 0 disables) and serves it at `GET /api/v1/fairshare/history`, scoped to one model or the aggregate. The Fairshare page loads that window on open and on every model-scope change, so a refresh no longer clears the chart. History is per gateway process and resets on restart.
- **Anthropic Messages API.** The gateway serves `POST /v1/messages` and `POST /v1/messages/count_tokens`, so Claude Code and Anthropic SDKs work by pointing `ANTHROPIC_BASE_URL` at the gateway and using a gateway key as `ANTHROPIC_API_KEY` (`x-api-key` or `Authorization: Bearer`). Streaming, system prompts, images, and tool use translate onto the existing chat pipeline; admission, budgets, boons, and billing apply unchanged, and usage is recorded with request type `messages`. Requests naming a model the gateway does not know are served by the new "Default model for Anthropic clients" routing setting, or return `not_found_error` when it is unset. System-role entries in `messages` are accepted and hoisted into the system prompt, and top-level `cache_control` is dropped before forwarding. Not supported in this release: prompt caching, extended-thinking control, image results inside tool results, and server-side tools. Previously `POST /v1/messages` was forwarded to the upstream unchanged; it is now translated by the gateway, so a deployment that relied on that pass-through must route those requests a different way.
- **Video generation (OpenAI Videos API).** A new `video` model type serves the job-based Videos API: `POST /v1/videos` creates a job (JSON, or multipart with a reference frame; OpenAI's field is `input_reference`, and the form is forwarded untouched), and `GET /v1/videos/{id}`, `GET /v1/videos/{id}/content`, `DELETE /v1/videos/{id}` and `GET /v1/videos` poll, download, delete and list. The create goes through the ordinary pipeline: model resolution, the tenant allowlist, input guardrails on `prompt` (uploaded frames are not scanned), fairshare admission, budgets, the upstream model-name swap and the model's upstream headers. It is billed the model's new flat `cost_per_video` once the upstream accepts the job, as request type `video`, and nothing when the create fails; it is never served from the response cache. On success the gateway records the job id against the model, the tenant, the key and the endpoint that accepted it, in Postgres (the new `video_jobs` table, not Redis, whose `volatile-lru` policy can evict a TTL'd key mid-render). **Jobs are private to the API key that created them by default:** a poll, download or delete matches the job id, the tenant and the caller's key, and the list holds only the caller's own jobs, so in a tenant of many users (each with their own secret key, or an SSO/JWT caller's per-user identity key) no user can list, poll, download or delete another's video. `OBLETH_VIDEO_JOB_SCOPE=tenant` (Helm `obleth.videoJobScope`, compose passes it through) shares jobs with every key of the tenant instead; an invalid value falls back to `key` with a startup warning. A disabled key is refused as before, and a rotated key is a new key, so under `key` scope neither reaches the old key's jobs, which expire with their records. Internal (probe) keys are scoped like any other key, never widened. The follow-ups are served from that record: they go back to the endpoint that holds the job, answer the same 404 for an unknown id, another tenant's job, and (under `key` scope) another key's job, without contacting the backend, pass the upstream status through unchanged (for example a not-ready response while the video renders), and stream the mp4 with its `Content-Type`, `Content-Length` and `Content-Disposition` without buffering it. Job ids are the upstream's to mint: any id of 1 to 256 printable characters is accepted except one containing `/`, `\`, `?`, `#` or `%`, or `.` and `..`, and it is percent-encoded as a single path segment when forwarded. They are authenticated and ownership-checked but take no fairshare slot and are neither billed nor written to the usage ledger. `DELETE` drops the record once the upstream confirms; the list is the upstream's listing filtered to the caller's jobs (the key's own, or the tenant's under `tenant` scope). Records are pruned after `OBLETH_VIDEO_JOB_RETENTION_HOURS` (default 24; Helm `obleth.videoJobRetentionHours`). Video models get no generation probe: like image models, their health check is the upstream catalog, and `/v1/models` and `/model/info` report them as `video_generation`. `cost_per_video` is settable on model create and update, in a manifest, and in the model form. Migrations 0027 (`models.cost_per_video`), 0028 (`video_jobs`) and 0030 (an index on `video_jobs (tenant_id, key_id, created_at desc)` for the per-key listing) are idempotent; the ledger and billing do not depend on the scope. Not yet handled: admission that counts outstanding renders rather than in-flight requests (a tenant can queue jobs up to the backend's own queue limit), billing on completion, and progress webhooks.
- **Image edits and variations work.** `POST /v1/images/edits` and `POST /v1/images/variations` send the source image as `multipart/form-data`, and the gateway never read the form, so every request failed with "model is required" before reaching the upstream. The form is now parsed like an audio upload: the model is resolved from its `model` field, the upstream model name is swapped in, and the file is forwarded unchanged. The model's `cost_per_image` is charged per image requested (the form's `n`, default 1), as for generations.
- **Per-model upstream headers.** A model can carry headers the gateway adds to every request to its upstream, after the client's forwarded headers so the operator's value wins a name both set: for example a routing hint an inference gateway reads, or a tenant or organization header a provider requires. They also go on the gateway's own calls to that model (tool loops, verdicts, knowledge embedding, health probes, auto-tune). Set them with `upstream_headers` on model create and update (a `null` value keeps the stored value for that name, `{}` removes them all, and omitting the field leaves them alone), in a manifest, or as `Name: value` lines under Upstream headers in the model form. Values are encrypted at rest and write-only: the Management API and manifest export return only `upstream_header_names`. `authorization` (use `api_key`), `host`, `content-length`, `content-type`, `accept-encoding`, and hop-by-hop headers are refused. Migration 0026 adds the column and is idempotent.
- **`GET /v1/models` lists the gateway's registry.** The listing used to be the union of every upstream's own catalog, so a model whose backend does not serve `/v1/models` (or was unreachable at that moment) was missing, and models a backend served but the gateway had not registered were listed under the backend's id even though requests for them are refused. It now lists every enabled route under its client-facing name, with the same fields as `GET /v1/models/{id}` (`model_type`, `mode`, `quantization`, `tags`, `aliases`, `owned_by: "obleth"`), without calling any upstream. Entries no longer carry an upstream's `created` timestamp or `owned_by` value. A tenant with a model allowlist now sees only the models it may call, as on `/model/info`, and `GET /v1/models/{id}` answers 404 for a registered model outside the allowlist instead of describing it.
- **A catalog the gateway cannot read no longer marks an image model down.** Image models have no inference probe (a generation is too costly to run every sweep), so their health check is whether the upstream catalog lists them. When the upstream answers the catalog request with a 4xx, for example a gateway that does not serve `/models` or guards it differently from inference, the model's health is now `unknown` instead of `unhealthy`: it stays routable, does not count toward the failure threshold, and does not alert. An upstream that does not answer at all is still `unhealthy`, and a catalog that answers without the model still is too.
- **obench puts the in-flight ceiling back.** Demo runs raise the gateway's global in-flight ceiling to fit the fleet they seed; they now restore the previous value at teardown instead of leaving it behind. The scorecard also seeds its demo models with pools wide enough for its concurrency ramp, so the overhead and capacity sections measure the proxy rather than the default 32-slot pool.
- **The auto router and the harm scanner answer through verdicts.** The router's classifier used to ask for a JSON object in free text and fell back to difficulty 1 whenever it didn't parse; it now asks one yes/no per routing tag plus a three-level difficulty score, read off first-token probabilities, and every failure still routes cheaper, never more expensive. The tier-2 harm scanner used to count any reply that didn't start with UNSAFE as safe; it now reads p(unsafe) off one token, and a model that doesn't answer returns an error, so the policy's `fail_open` decides instead of the content passing. `log_only` alerts report p(unsafe). A guardrail policy with `fail_open: false` now blocks when its guard model doesn't answer, where before the request went through.
- **Image generation stays quiet until asked, and follow-ups draw.** The image tool's nudge is now background guidance with an explicit don't-advertise clause, so a bare greeting no longer gets an image-generation pitch. A generated image is replayed to the model as a receipt of the tool call that made it, so a follow-up image request calls the tool instead of answering in prose.

**Security and safety fixes from a full audit**

- **Tenant guardrails apply on every text path.** The `x-obleth-boons: off` header now turns off boons only; the tenant's input and output guardrails still run. Input guardrails scan every message except the model's own turns and tool output (so `developer` messages are covered), plus the text fields of non-chat requests (`prompt`, `input`, `query`, `documents`), and run on `POST /v1/verdicts` before admission. Embedding, rerank, and moderation inputs therefore now pass through every configured input scanner, including the harm guard model: under a block policy, indexing a document that trips a scanner returns 400. POST requests to `/responses`, `/messages`, `/verdicts`, and spellings with repeated or trailing slashes are handled like their canonical `/v1` forms instead of being forwarded unscanned. Under an input policy the auto-router's classifier is not called (routing uses the effort header and heuristics). Under a block or redact input policy, a completion prompt given as token ids and a POST to an unrecognized path both return 400. Output guardrails with the block or redact action read chat responses only, so under such a policy endpoints that may return other generated text (`/v1/completions`, audio transcription and translation, unrecognized paths) return 400. The text fields of multipart forms (the image-edit and transcription `prompt`) are scanned like a JSON body, and a redaction is applied to the forwarded form. Not scanned: uploaded files (audio and images) and embedding inputs given as token ids.
- **Secrets stay on the server.** The tenant portal no longer receives upstream URLs or keys, the audit log no longer records a model's upstream key on creation, and the Slack webhook URL is kept out of alert error messages. Every dashboard page checks the admin role itself instead of relying on the layout.
- **Revoking a key really revokes it.** Deleting or disabling a key, tenant, model, MCP server, or alias now fails with 502 if the Redis eviction fails, rather than silently leaving the old entry serving; the message names the new `POST /api/v1/resync`, which rebuilds and prunes the cached keys, models, and MCP servers from Postgres. The dashboard shows that error on the affected page.
- **The MCP gateway applies the full tenant gate.** Suspended, expired, or out-of-window tenants can no longer reach registered MCP servers. `POST /v1/responses` authenticates before reading the request body.
- **The provisioner holds on uncertainty.** A Management API error is no longer read as "no models" or "no replicas" (which drained or double-submitted the fleet); a slurmrestd 404 counts as job-gone only when the body says so; and if every tracked job vanishes in one tick the reconciler holds and alerts instead of marking the fleet lost. Slurm and Management API calls carry timeouts.
- **Outbound URL policy covers every destination.** The verify URL, the speculation URL template, the slurmrestd URL, and restored settings go through the same checks as `api_base`; Alibaba's metadata address and NAT64 / IPv4-compatible forms are blocked; hostname resolution no longer blocks a runtime worker. The speculation template accepts placeholders in the host and path but never in the scheme or credentials, and a substituted value cannot introduce an address literal.
- **Endpoint edits are scoped to their model.** Updating or deleting an endpoint under the wrong model returns 404 instead of editing another model's endpoint and desynchronising its cache. Usage retention is capped at 36,500 days (a larger value crashed the retention worker); two usage filter combinations that returned 500 now work.
- **Dashboard account hardening.** Email sign-up is closed (the break-glass admin is seeded directly); an admin cannot deactivate or demote themselves or the last active admin; portal users can disable a key but not re-enable one an administrator disabled; CSV exports neutralise spreadsheet formulas; provider import refuses redirects and link-local targets and times out after 5 s. Mutations made through live dashboard routes now carry the acting user in the audit log.
- **Kubernetes chart.** The telemetry spill file gets a writable volume (it was unwritable, so usage rows were lost whenever ClickHouse was down); datastore passwords come from Secrets; bundled datastores have probes and resource limits; a startup probe covers slow boots; the network policy admits the dashboard to Postgres and guards Redis and the admin port; pods roll when the Secret changes; the PDB renders only when more than one replica is guaranteed; the Helm chart publishes only after its images exist.

**Reliability and billing fixes from a full audit**

- **Term-budget usage is never evicted.** Committed monthly and term usage in Redis no longer carries a TTL, so a full Redis under the chart's `volatile-lru` policy can no longer evict it and reset a tenant's or key's spend mid-period. Existing counters drop their old one-year TTL on their next update.
- **Knowledge uploads up to the configured size.** The document upload route accepted about 1.5 MB of file regardless of the upload setting, and the dashboard cut uploads off at about 7.5 MB. Both now accept the full configured size. The setting is capped at 50 MiB.
- **Failed requests are not billed.** An upstream 4xx or 5xx without a usage block records zero tokens and zero cost; a 502 or 504 refunds the admission-time reservation; a request blocked by a guardrail settles and releases its permit. A stream that ends before the terminal chunk now returns 502 and bills the usage the upstream reported, or the prompt estimate plus the streamed text when it reported none. Energy is attributed from the slot time the request actually held, on every outcome. The gateway always asks upstreams for stream usage and strips the extra chunk when the client did not request it.
- **Term budgets reserve, then reconcile.** Monthly and term budgets are reserved at admission (estimated tokens and cost) and corrected to the real figures at completion, so concurrent requests cannot collectively exceed a term budget. Reservations that never settle expire after ten minutes. Helper calls made on a request's behalf (vision, structured output, tool loops, drafts, image generation) now count against the tenant's and key's term budgets.
- **Helper calls follow the model's endpoints.** Boons that call the target model (tool loops, classification, speculative drafting, image generation, knowledge embedding) route through a healthy endpoint with that endpoint's key instead of the model-level `api_base`, so managed models with no `api_base` work with every boon. Tool loops are capped at 16 tool calls per turn and a per-request deadline (`deadline_secs`, default 300, maximum 3600, editable through the boon settings API); a session that fails once is not retried within the same request; MCP discovery failures are cached for 45 s; helper responses are read with size caps.
- **Queued requests time out.** A request that waits longer than `OBLETH_ADMISSION_TIMEOUT_SECS` (default 60) in the fairshare queue returns 503 with `Retry-After` instead of holding the client indefinitely. The scheduler drops pools for models that are no longer routed, keeps weighted caps from rounding to zero, and skips waiters whose client has gone.
- **Graceful shutdown.** On SIGTERM the gateway stops accepting connections, drains in-flight requests for up to `OBLETH_SHUTDOWN_GRACE_SECS` (default 300), flushes telemetry, and exits; the compose and Helm stop grace periods cover the whole sequence. The provisioner exits cleanly on SIGTERM between ticks.
- **Redis and upstream timeouts.** Redis commands and connections are bounded (`OBLETH_REDIS_RESPONSE_TIMEOUT_MS`, default 250; `OBLETH_REDIS_CONNECT_TIMEOUT_MS`, default 2000), so a stalled Redis surfaces as a fast 503 instead of a hung request; a Redis error during key lookup now returns 503 rather than 401. The gateway re-pushes its configuration to Redis every `OBLETH_REDIS_REWARM_SECS` (default 300) and after every pub/sub reconnect, prunes entries that no longer exist in Postgres, and re-subscribes on a silent channel, so a Redis restart or eviction no longer leaves keys unknown until the next admin write. Upstream responses that stop mid-body time out after `OBLETH_UPSTREAM_READ_TIMEOUT_SECS` (defaults to the upstream request timeout, at least 120 s; 0 disables). The wait for upstream response headers (`OBLETH_UPSTREAM_TIMEOUT_SECS`, default 300) is now settable through the Helm value `obleth.upstreamTimeoutSecs` and forwarded by the compose file.
- **Telemetry survives ClickHouse outages.** The gateway boots without ClickHouse and spills usage rows to its local write-ahead file until the ledger returns; spill files are reused instead of created per batch; a corrupt line is quarantined by itself rather than discarding its file; replay is idempotent (duplicate batches are rejected by ClickHouse, including in the daily rollup); non-finite energy values are stored as zero; the daily-rollup view is rebuilt only when its definition changed, and the backfill runs once. Usage rows are always written to the spill file on failure, regardless of `OBLETH_FAIL_OPEN`, and a schema setup that keeps failing is reported at warning level rather than silently.
- **Management API and dashboard.** Changing a group's fairshare weight re-pushes only that group's keys; per-key usage summaries are scoped to the key's tenant; usage series are capped at 5000 buckets; clearing a provisioning error is audited; the last-admin guard also covers the account admin endpoints. Settings → Data and backups has "Reconcile cache…", which runs `POST /api/v1/resync`.

## v1.2.0

The Responses API, boons that compose per request, and model names free of their serving format.

- **`POST /v1/responses` works on every model.** The gateway serves the OpenAI Responses API by translating to chat completions and back at the edge, so any registered model — and any client that only speaks Responses, OpenWebUI included — works without the backend knowing the surface exists. Input items, `instructions`, `max_output_tokens`, `text.format`, and tools all map across; streaming is re-emitted in the full Responses event vocabulary with contiguous sequence numbers, and a reasoning model's scratchpad arrives as proper `reasoning` output items rather than being dropped. The translation is stateless by design: `store`, `previous_response_id`, and `background` are rejected with a clear 400 instead of being silently ignored, so nothing is ever persisted that a client believes it can retrieve later. Telemetry records which surface a request came through.

- **Boons compose per request instead of per grant.** Granting a model image generation no longer costs it speculation on every other request: the image tool only claims the response pipeline when the request actually calls for an image, and the draft-verify cascade keeps accelerating everything else. When the image tool is armed but the request's intent can't be classified in time, speculation stands down rather than racing a possible tool call.

- **A generated image no longer eats the next turn's context.** The playground used to replay a generated image into the following request as raw base64 text — half a million tokens of it, blowing the context window of the very model that produced it. The dashboard now replays a compact placeholder (and re-attaches the newest generation as a real image part when the model can see it), and the gateway independently strips replayed attachment bytes out of prompts, so third-party clients are covered too.

- **The models catalog is reachable however the backend spells it.** Gateways that mount their catalog only at `/v1/models/` (AIBrix's metadata service among them) no longer break obleth: health checks and model validation retry with the trailing slash, `GET /v1/models` lists every route instead of dropping the ones behind such a gateway, and the collection endpoint answers the listing regardless of what a client puts in the request body. Creating a model against a healthy backend no longer fails its upstream validation.

- **The router understands cost and vision.** Routing decisions now score each candidate's per-request cost, models without vision are hard-filtered from requests that carry images, and hybrid tiers are derivable from the models themselves. A routing readiness card in the dashboard lints the configuration before it bites, and simulate can exercise the live classifier instead of only the heuristics.

- **Dashboard polish.** Generated images render in place instead of blanking their data URLs, Settings says outright when a granted boon is switched off globally, and the provider table shows real vendor marks for the twenty-seven providers that were falling back to an initial.

- **Model names no longer have to carry the serving format.** A model's weight/activation format is now a field on the route — `quantization`, from a fixed vocabulary (`fp8`, `mxfp4`, `awq`, `gguf`, …) — instead of something operators had to spell into the name clients call. A model can also answer to **aliases**: extra client-facing names that resolve to the same route, so `glm-5-3-mxfp4` can be renamed to `glm-5-3` with the old spelling registered as an alias and every pinned client left working. An alias costs nothing per request (it resolves in the same single cache lookup as the canonical name) and is folded to the canonical name before accounting, so a model's usage is no longer split across the spellings clients happen to use. `GET /v1/models` now reports the gateway's clean name for a backend that only knows itself by its quantized one, lists each route once, and carries `quantization`, `tags`, and `aliases` on every entry it recognizes.

- **A new `GET /model/info` endpoint.** Served from the gateway's own registry rather than from the backends, so it lists every registered model whether or not its backend answers this second, and reports the facts a client cannot infer from a name: serving format, routing tags, context window, per-token and per-unit prices, capability flags, granted boons, aliases, and last-observed health. The envelope keeps the familiar `/model/info` shape so existing tooling picks it up, but the per-route facts live under `obleth_params` — obleth's own key, carrying fields like `quantization` that the conventional shape has no place for. Available at both `/model/info` and `/v1/model/info`, and it never reports how to reach a backend. Tenants with a model allowlist see only the models they may call.

- **Provider import lifts the format out of discovered names.** Importing a catalog that advertises `Qwen/Qwen3-8B-FP8` now suggests `qwen3-8b` with `quantization: fp8` and the provider's full id pre-filled as an alias, instead of registering the suffix as part of the name.
